Use this specification to inspect Nebula traffic or implement a peer that interoperates with protocol version 15. It defines the application payload carried by Nebula's LiteNetLib connections. LiteNetLib packet headers, acknowledgements, fragmentation, and connection negotiation are outside this specification.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** describe interoperability requirements. The source of truth for this version is `Packages/com.1by3.nebula/Runtime/Protocol/Messages.cs`.

## Compatibility

The current protocol version is `15`. Every `Hello` carries that version.

- A gateway disconnects a client whose version is not exactly `15`. There is no feature negotiation or backward-compatible field skipping.
- Only the gateway's inbound `Hello` path currently enforces exact equality. The normal gateway-to-worker and worker-to-worker handlers read the version without rejecting a mismatch. Run every service process from the same build.
- A change to a message identifier, field order, primitive encoding, or field meaning is incompatible and requires a protocol-version change.
- The protocol does not include a game-schema identifier. Every peer MUST use matching prefab identifiers, behavior order, `NetworkVariable` order and types, remote procedure call (RPC) methods, input types, and custom sync-state formats.

Unsigned tick and entity-epoch comparisons do not include wraparound handling. A process that remains up across a `u32` wrap is outside the current compatibility contract.

## Transport contract

Nebula uses LiteNetLib over User Datagram Protocol (UDP). A connection request uses the plaintext key `nebula-v1`. This key is a protocol discriminator, not a credential.

| Nebula delivery | LiteNetLib channel | LiteNetLib method | Contract |
| --- | ---: | --- | --- |
| `Sequenced` | 0 | `Sequenced` | Unreliable and newest-wins. A packet larger than the peer's maximum transmission unit cannot be fragmented and is dropped. |
| `ReliableOrdered` | 1 | `ReliableOrdered` | Retried and delivered in order. LiteNetLib may fragment it. |

Except for `Batch`, one LiteNetLib application payload contains one complete Nebula message. The first byte is always its `MsgId`. A sender MUST use the delivery class listed below; the receiver does not derive or verify the class from the payload.

### Web clients

A client built for the web connects to the gateway over WebRTC data channels instead of LiteNetLib. It sends its Session Description Protocol (SDP) offer as the body of `POST /nebula/rtc` on the gateway's web port and applies the SDP answer from the response. The gateway answers as an ICE-lite endpoint with DTLS role `passive` and lists its host candidates. Both data channels are created with `negotiated: true`, and every message is binary.

| Nebula delivery | Data channel | Options | Contract |
| --- | ---: | --- | --- |
| `Sequenced` | id 1 | `ordered: false`, `maxRetransmits: 0` | Each message starts with a `u16` sequence number that increases by one per message and wraps. A receiver MUST drop a message whose number is not newer than the newest it delivered; a number is newer when it differs and `(number - newest) mod 65536` is below 32768. The Nebula message follows the two bytes. |
| `ReliableOrdered` | id 0 | reliable, ordered | One data channel message contains one Nebula payload, as on LiteNetLib. |

<Callout type="warn" title="The wire is not secure">
LiteNetLib connections are not encrypted. WebRTC encrypts a web client's link with DTLS, but the gateway accepts every offer. A peer can claim any role, process identifier, worker index, or client name in `Hello`. A client's `token` and `session` are checked (see [Authentication](/docs/guides/authentication)), and a gateway or worker must present a credential derived from the mesh token when the mesh has one; all of them travel in the clear on a LiteNetLib link. Without a mesh token, every gateway and worker peer is accepted. Run service links on a trusted private network, and put public client traffic behind ingress that supplies the security your game requires.
</Callout>

## Primitive encodings

All fixed-width numbers are little-endian. No field is naturally aligned and no padding bytes are inserted.

| Type | Bytes | Encoding |
| --- | ---: | --- |
| `u8`, `s8` | 1 | Unsigned byte or two's-complement signed byte. |
| `u16`, `s16` | 2 | Unsigned or two's-complement signed integer. |
| `u32`, `s32` | 4 | Unsigned or two's-complement signed integer. |
| `u64`, `s64` | 8 | Unsigned or two's-complement signed integer. |
| `f16` | 2 | IEEE 754 binary16. |
| `f32` | 4 | IEEE 754 binary32. |
| `f64` | 8 | IEEE 754 binary64. |
| `bool` | 1 | Writers emit `0` for false and `1` for true. Readers treat any nonzero value as true. |
| `string` | variable | A `u16` prefix `n`, followed by `n - 1` UTF-8 bytes. `n = 0` is null and `n = 1` is empty. At most 65,534 UTF-8 bytes. |
| `bytes` | variable | A `u16` byte count followed by that many bytes. Null and empty both encode as a zero count. At most 65,535 bytes. |
| `vector2` | 8 | `f32 x`, then `f32 y`. |
| `vector3` | 12 | `f32 x`, `f32 y`, then `f32 z`. |
| `quaternion` | 16 | `f32 x`, `f32 y`, `f32 z`, then `f32 w`. |
| `color` | 16 | `f32 r`, `f32 g`, `f32 b`, then `f32 a`. |

An enum written through `NetworkSerialization` is an `s32`, but protocol enums and flags use the field width shown in each layout.

### Compressed quaternion

A compressed quaternion occupies one `u32`. Normalize the quaternion, find the component with the greatest absolute value, and negate all components when that component is negative. Ties select the earliest component in `x, y, z, w` order. Bits 31–30 contain the omitted component's index (`x = 0`, `y = 1`, `z = 2`, `w = 3`). The remaining components, in `x, y, z, w` order with the selected component omitted, occupy bits 29–20, 19–10, and 9–0.

For each stored component `v`, encode:

```text
r = 1 / sqrt(2)
q = clamp(round_to_nearest(((clamp(v, -r, r) + r) / (2 * r)) * 1023), 0, 1023)
```

Decode each ten-bit value with `(q / 1023) * (2 * r) - r`. Reconstruct the omitted, nonnegative component as `sqrt(max(0, 1 - a*a - b*b - c*c))`.

## Shared identifiers and structures

### Entity identifiers and epochs

`net_id` is a `u64`. A worker allocates it as `(worker_index << 48) | sequence`, where `worker_index` supplies the high 16 bits and `sequence` increases from 1 in the low bits. Zero means that no entity is assigned.

An entity authority epoch is a `u32` and starts at 1. It increases on every handover. Receivers ignore entity state whose epoch is older than the newest epoch they have accepted. This is separate from the `u64` lease epoch in the [control-plane contract](/docs/specifications/control-plane).

`client_id` is a `u64` session identifier that is unique across every gateway of a mesh. A gateway draws a random 32-bit **incarnation** when it starts and numbers its sessions from 1: `client_id = (incarnation << 32) | sequence`. Zero means no owner in an entity record and broadcast in an `EntityRpc`. The gateway replaces the `client_id` supplied by a client in `ClientInput` and `ServerRpc` with the session ID of that connection. A session ID stays the same when the client reconnects with its session token, through any gateway of the mesh (see [`Hello` and session messages](#hello-and-session-messages)).

### Container reference

A `ContainerRef` starts with a `u16 index`.

| Index | Meaning | Following bytes |
| ---: | --- | --- |
| `0` through `65532` | Static container's dense registry index. | None. |
| `65533` | Runtime container registered by the game. | `u64 runtime_id`. |
| `65534` | Dynamic container carried by an entity. | `u64 carrier_net_id`. |
| `65535` | No container. | None. |

Positions and rotations are relative to this container unless a behavior's documented payload says otherwise. A peer may receive a dynamic or runtime reference before it can resolve the container; Nebula holds affected entity messages until that container arrives.

### Role and entity flags

| Field | Value | Meaning |
| --- | ---: | --- |
| `PeerRole.Unknown` | 0 | Unidentified peer. |
| `PeerRole.Client` | 1 | Game client. |
| `PeerRole.Gateway` | 2 | Gateway service. |
| `PeerRole.Worker` | 3 | Simulation worker. |
| `HelloFlags.Bot` | 1 | The client is a headless bot. |
| `EntityFlags.OwnerIsBot` | 1 | The owning client is a bot. |
| `EntityFlags.ServerDriven` | 2 | The entity has no client owner and is driven by a worker. |

Unknown flag bits are reserved. A version 15 sender MUST write them as zero.

## Message layouts

The layouts below omit the leading `u8 msg_id`. Fields appear in wire order. Repeated structures have no padding.

### Hello and session messages

```text
Hello           := u16 protocol_version, u8 role, string id, u32 index, u8 flags,
                   string token, string session, u32 incarnation
Welcome         := u64 client_id, u8 tick_rate, u32 server_tick, string identity,
                   string token, string session_token, bool reclaimed
JoinStatus      := u8 state, u16 estimated_seconds
JoinRejected    := string reason, bool retry
GatewayDraining := u16 reconnect_within_seconds
SessionReplaced := string reason
Ping            := f64 client_time
Pong            := f64 client_time, u32 server_tick
```

For a client, `Hello.id` is the requested player name, `index` is zero, `flags` may include `Bot`, `token` is an OpenID Connect ID token, a token from an earlier `Welcome`, or empty to ask for a new anonymous identity, `session` is the `session_token` from the last `Welcome` or empty on a first connection, and `incarnation` is zero.

For a worker, `id` is the worker ID and `index` is its worker index. A gateway sends its gateway ID with an index of zero. Both send a nonzero `incarnation`, a random number drawn when the process started, so a peer that sees the same ID twice can tell a restart from a reconnect. When the mesh has a mesh token, `token` on a gateway or worker `Hello` is the credential `unix_seconds.base64url(HMAC-SHA256(key, role|id|incarnation|unix_seconds))`, where `key = SHA-256("nebula-peer-auth:" + mesh_token)` and `role` is the decimal `PeerRole` value. A receiver rejects a credential whose timestamp differs from its clock by more than 300 seconds or whose MAC does not match. Without a mesh token, `token` is empty and every peer is accepted.

The gateway assigns the client ID, a mesh-wide session ID, and sends the fixed tick rate, currently `60`, in `Welcome`. `Welcome.identity` is the player's identity: 64 lowercase hex characters, the SHA-256 of the token's issuer and subject. `Welcome.token` is set only when the client presented no token; it is the anonymous token the gateway issued for that identity, which the client keeps for its next `Hello`. `Welcome.session_token` is a signed token naming the session: an HS256 JSON Web Token over the session ID, identity, display name, bot flag, and connection generation, valid for 24 hours. The client keeps it for the life of the process and presents it as `Hello.session` when it reconnects. A gateway that verifies it, for the identity that just authenticated, welcomes the client with the same `client_id` and sets `reclaimed`; the pawn is the same one when the worker still holds it. A session token for another identity, an expired one, or one signed for another mesh is ignored and a new session starts. See [Authentication](/docs/guides/authentication).

`JoinStatus.state` is `0` (none), `1` (starting: welcomed, but no worker holds a lease yet) or `2` (joined). `estimated_seconds` is a rough wait while starting; `0` means unknown.

A gateway that does not accept a client's token sends `JoinRejected` with a reason fit to show the player and disconnects the client. `retry` set means the refusal is about the gateway, not the client: it is draining, and the client SHOULD reconnect after a short delay, which a load balancer then hands to another gateway. `retry` clear means the client's credentials were refused and retrying with the same ones is pointless.

`GatewayDraining` tells a connected client that the gateway is leaving service. The client SHOULD reconnect within `reconnect_within_seconds`, presenting its session token, so the session and pawn carry over to the gateway that answers.

`SessionReplaced` tells a client that the player it signed in as connected again elsewhere and that the newer connection now holds the session and the pawn. The gateway closes the link after sending it. The client SHOULD show `reason`, discard its session token, and stay out of the world until the player asks to return; reconnecting on its own would take the session back from the other connection, which would then take it back in turn. See [One connection per player](/docs/guides/authentication#one-connection-per-player).

`Pong.client_time` echoes `Ping.client_time`. `server_tick` is the gateway's current derived tick.

### Entity lifecycle and variables

```text
EntitySpawnBody :=
  u64 net_id,
  u16 prefab_id,
  u64 owner_client_id,
  ContainerRef container,
  u32 entity_epoch,
  u16 owner_worker_index,
  vector3 local_position,
  quaternion local_rotation,
  vector3 local_scale,
  vector3 velocity,
  u8 entity_flags,
  u32 scene_id,
  bytes vars,
  bytes state,
  string owner_identity

EntityDespawnBody := u64 net_id, u32 entity_epoch
EntityVarsBody    := u64 net_id, u32 entity_epoch, bytes vars
```

`EntitySpawn` and `GhostSpawn` share `EntitySpawnBody`. A nonzero `scene_id` tells the receiver to bind its matching scene object instead of instantiating `prefab_id`. A spawn for a known `net_id` updates that entity's owner, epoch, container, variables, and sync state; it does not create a duplicate. `owner_identity` is the owning player's identity (see `Welcome`), or empty for an entity no player owns.

The `vars` blob concatenates every `NetworkVariable` in deterministic behavior and reflected field order. It carries no count, names, type tags, or per-value lengths. A compatible game schema is therefore required. `state` is a [sync-state envelope](#sync-state-envelope).

### Behavior sync state

```text
EntitySyncBody :=
  u64 net_id,
  u32 entity_epoch,
  u32 tick,
  ContainerRef container,
  bool reliable,
  bytes chunks
```

`EntityState` and `GhostSyncState` share this body. A sender MUST use reliable ordered delivery when `reliable` is true and sequenced delivery when it is false. `chunks` contains a sync-state envelope.

#### Sync-state envelope

```text
SyncStateEnvelope := u8 chunk_count, Chunk[chunk_count]
Chunk             := u8 behavior_index, u8 flags, u16 byte_length, raw[byte_length]
```

Chunk flag bit 0 (`Full`) marks a keyframe. Bits 1–7 are reserved. The raw chunk is defined by that behavior's `WriteSyncState` and `ReadSyncState` pair. Receivers skip an unknown behavior index and bound each reader to `byte_length`.

Spawn snapshots contain a full chunk for every sync behavior except the root `NetworkTransform`. Per-tick sequenced sync streams send a full keyframe every 30 ticks. The root transform uses `WorldState` and `GhostState` instead.

### Remote procedure calls

```text
EntityRpcBody :=
  u64 net_id,
  u32 entity_epoch,
  u8 behavior_index,
  u32 method_hash,
  u64 client_id,
  bytes args
```

`EntityRpc`, `ServerRpc`, and `AuthorityRpc` share this body. `method_hash` is 32-bit FNV-1a over the RPC method name's UTF-16 code units: start at `2166136261`, then for each code unit XOR its value and multiply by `16777619` with `u32` overflow. Overloads are not supported.

Arguments are concatenated in declaration order using `NetworkSerialization`; there is no argument count or type tag. `EntityRpc.client_id = 0` broadcasts to all clients, while a nonzero value selects one client. The gateway overwrites `ServerRpc.client_id` with the sending connection's session ID and only forwards a call for an entity that connection owns. A worker accepts a `ServerRpc` for a session only from the gateway that currently holds that session.

### Batched transform state

```text
StateBatchBody   := u32 tick, u16 worker_index, u16 entry_count, EntityStateEntry[entry_count]
EntityStateEntry := u64 net_id, u32 entity_epoch, ContainerRef container,
                    u16 fields, conditional_transform_fields
```

`WorldState` and `GhostState` share this body. Writers group entries with the `Reliable` flag into reliable ordered packets and all other entries into sequenced packets. A packet MUST NOT mix the two classes.

The `fields` mask controls the rest of each entry:

| Bit | Hex | Name | Meaning |
| ---: | ---: | --- | --- |
| 0 | `0x0001` | `PositionX` | Include position X. |
| 1 | `0x0002` | `PositionY` | Include position Y. |
| 2 | `0x0004` | `PositionZ` | Include position Z. |
| 3 | `0x0008` | `RotationX` | Include Euler X, or indicate that rotation is present in quaternion mode. |
| 4 | `0x0010` | `RotationY` | Include Euler Y, or indicate that rotation is present in quaternion mode. |
| 5 | `0x0020` | `RotationZ` | Include Euler Z, or indicate that rotation is present in quaternion mode. |
| 6 | `0x0040` | `ScaleX` | Include scale X. |
| 7 | `0x0080` | `ScaleY` | Include scale Y. |
| 8 | `0x0100` | `ScaleZ` | Include scale Z. |
| 9 | `0x0200` | `Velocity` | Include all three velocity axes as `f16`. |
| 10 | `0x0400` | `Teleport` | Clear interpolation and snap. Adds no bytes. |
| 11 | `0x0800` | `Half` | Encode selected position, Euler rotation, and scale axes as `f16` instead of `f32`. |
| 12 | `0x1000` | `Quaternion` | Encode rotation as one quaternion rather than selected Euler axes. |
| 13 | `0x2000` | `Compressed` | With `Quaternion`, use the compressed `u32` form. |
| 14 | `0x4000` | `Reliable` | Send this entry on reliable ordered delivery. Adds no bytes. |
| 15 | `0x8000` | `Location` | Complete location keyframe, including a container or epoch change. Snap and accept the supplied local pose. Adds no bytes. |

After `fields`, write data in this order:

1. Selected position axes, X then Y then Z, as `f16` when `Half` is set and `f32` otherwise.
2. Rotation, only when at least one rotation bit is set. Without `Quaternion`, write the selected Euler axes in X/Y/Z order and honor `Half`. With `Quaternion | Compressed`, write one compressed `u32`. With `Quaternion | Half`, write four `f16` components. With `Quaternion` alone, write a normal quaternion.
3. Selected scale axes, X then Y then Z, honoring `Half`.
4. When `Velocity` is set, write X, Y, and Z as three `f16` values regardless of `Half`.

### Prediction messages

```text
ClientInputBody := u64 client_id, u8 frame_count, InputFrame[frame_count]
InputFrame      := u32 tick, bytes payload

OwnerState :=
  u64 net_id,
  u32 entity_epoch,
  u32 tick,
  u32 last_input_tick,
  s8 input_lead,
  u64 owner_client_id,
  ContainerRef container,
  bytes state
```

`ClientInput` and `ForwardInput` share `ClientInputBody`. A worker accepts `ClientInput` for a session only from the gateway that currently holds that session. The stock client repeats up to its three newest frames to tolerate loss. Each input payload is the exact output of the game's `INetworkInput.Serialize` method.

`OwnerState.state` is the exact output of the predicted behavior's `WriteState`. `input_lead` is the smallest observed `input_tick - worker_tick` since the previous report, clamped to `-127` through `127`. `-128` means that no input arrived during the reporting window.

### Container ownership

```text
ContainerOwnership := u16 entry_count, OwnershipEntry[entry_count]
OwnershipEntry :=
  u16 container_index,
  string container_id,
  u16 worker_index,
  string worker_id,
  u64 lease_epoch,
  string lease_state,
  bool has_instance,
  [InstanceContainerInfo when has_instance],
  u8 flags,
  [vector3 bounds_center, vector3 bounds_size when flags bit 0 is set]
```

Flag bit 0 (`Bounds`) marks a runtime container and appends its axis-aligned box in absolute world coordinates. Other bits are reserved. An empty `worker_id` represents an unassigned lease. Lease states and transitions are defined by the [control-plane contract](/docs/specifications/control-plane).

### Instance preparation

```text
InstanceContainerInfo := u64 instance_id, string content_resource,
  bool observe_public, vector3 observation_center, vector3 observation_size
InstancePreparation := u32 request_id, u64 entity_id, ContainerRef destination,
  u16 source_worker, u64 lease_epoch, bool success
```

Preparation asks the destination worker and owning client to load content before crossing. The gateway routes requests only for a pawn owned by the sending worker and routes replies only for the sending client's pawn. The source validates the request, destination lease, and authority before committing. Observation bounds are in absolute world coordinates.

### Reliable message batch

```text
Batch := u16 message_count, BatchedMessage[message_count]
BatchedMessage := u16 byte_length, raw_message[byte_length]
```

Each `raw_message` is a complete Nebula message, including its `u8 msg_id`, and its length MUST fit in a `u16`. The gateway uses `Batch` only for reliable gateway-to-client traffic. It flushes at about 1,100 bytes or by the end of the current transport poll, preserving reliable-message order.

### Player lifecycle

```text
SpawnPlayer   := u64 client_id, ContainerRef container, string name, bool is_bot, string identity, u64 generation
DespawnPlayer := u64 client_id, u64 generation
EndSession    := u64 client_id, u64 generation, string reason
```

The gateway selects a currently assigned container and asks its worker to spawn the player. `identity` is the player's identity as the gateway established it from the client's `Hello`. The game supplies the actual spawn behavior.

`SpawnPlayer` is also the message by which a gateway claims a session. `generation` is the session's connection generation: every time a client connects or reconnects, the gateway sets it to a value newer than any the session had before. A worker that already holds a pawn for `client_id` re-announces it to the sender with `EntitySpawn` and, when `generation` is newer than the one it holds, routes the session's input and RPCs through the sender from then on. A worker MUST ignore a `SpawnPlayer` or `DespawnPlayer` whose `generation` is older than the one it holds. This fences a gateway that lost the client from undoing what the gateway that gained it did.

On `DespawnPlayer`, or when a gateway's link is lost, a worker keeps the pawn for `NebulaConfig.SessionReclaimSeconds` (default 30) and despawns it afterwards unless a newer `SpawnPlayer` reclaimed the session. With the setting at `0` it despawns the pawn at once.

A mesh with `NebulaConfig.SingleSessionPerPlayer` set, the default, keeps one connection per player. A gateway that welcomes a client for an identity it can already find in the world — in another connection of its own, or on the owner of any entity it knows — claims that session again instead of asking for a second pawn, and closes the connection that held it with `SessionReplaced`. A worker whose session is claimed by a different gateway sends `EndSession` to the gateway that held it, naming the claim's `generation`, so that gateway lets its client go the same way and MUST NOT despawn the pawn. A gateway MUST ignore an `EndSession` whose `generation` is older than the one it holds for the session. A worker that receives claims for one identity under two sessions keeps the one whose `generation` is newer and despawns the other's pawn. With the setting clear, every connection gets its own session and pawn.

### Authority transfer

```text
AuthorityTransfer :=
  EntitySpawnBody entity,
  u32 new_epoch,
  bytes pending_inputs,
  bytes handover_state,
  u16 ghost_worker_count,
  string ghost_worker_id[ghost_worker_count],
  u64 session_generation,
  string session_gateway
```

`session_generation` and `session_gateway` describe the owner's session as the sender knew it: the connection generation and the gateway key `<gateway_id>#<incarnation>` of the gateway that holds the session, so the receiving worker accepts input from that gateway at once. They are `0` and empty for an entity no client owns.

The nested entity body's `entity_epoch` and `new_epoch` are the same in messages emitted by version 15. `pending_inputs` is empty for an entity without a predicted behavior. Otherwise it has this layout, where each game-defined input has no length prefix:

```text
PendingInputs := u32 last_processed_input_tick,
                 u16 input_count,
                 PendingInput[input_count],
                 bool has_last_input,
                 [GameInput last_input when has_last_input is true]
PendingInput  := u32 tick, GameInput input
```

The stock predicted behavior sends at most 128 pending inputs. `GameInput` is the exact output of the game's `INetworkInput.Serialize` method.

`handover_state` has this envelope:

```text
HandoverState := u8 behavior_count, HandoverChunk[behavior_count]
HandoverChunk := u16 byte_length, raw[byte_length]
```

Chunks appear in behavior-index order. Their bytes are defined by each behavior's `WriteHandoverState` and `ReadHandoverState` pair. A receiver bounds each behavior to its chunk and skips chunks beyond its behavior count.

### Worker-defined messages

```text
WorkerMessage := u16 kind, raw_payload_to_end_of_message
```

The game assigns `kind` and defines the remaining bytes. `SendToWorker` selects either delivery class; reliable ordered is the default. Kind registration and the payload schema MUST match on both workers.

## Receiver behavior

Peers send `Hello` before role-specific traffic. A worker ignores non-`Hello` messages until it has received one. A gateway likewise ignores client traffic until it has accepted that connection's `Hello` and marked the client welcomed.

Nebula readers throw on a truncated field. The client, gateway, and worker catch malformed-packet exceptions, log them, and continue polling. They log unknown or directionally unexpected message IDs. They do not require every message handler to consume all trailing bytes, so a compatible sender MUST still omit unspecified trailing data.

The gateway validates client ownership before forwarding `ServerRpc`, stamps session IDs, filters transform state by current worker ownership and epoch, and rejects older entity updates. A worker accepts input and `ServerRpc` for a session only from the gateway that holds it, and ignores player claims and despawns with an older generation. These checks limit accidental stale traffic and fence out a gateway that lost a session. Only the mesh peer credential authenticates a service peer, and only when a mesh token is configured.
