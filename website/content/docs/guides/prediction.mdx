---
title: Prediction and reconciliation
description: Predict an owned entity, reconcile it with worker state, drive server-owned entities and vehicles, and perform lag-compensated queries.
---

Use `PredictedBehaviour<TInput>` for an entity that must respond to local input before a worker reply arrives. A player controller is the common example; a vehicle the player drives is another (see [Drive a vehicle](#drive-a-vehicle)).

Keep `NetworkIdentity` and an enabled `NetworkTransform` on the controller's root. A newly added predicted behavior requires and adds the transform component; check existing prefabs explicitly. Use worker authority (`Authority = Server`) so remote clients and ghost workers follow the worker's state. The owning client uses reconciliation. Do not combine this controller with `NetworkRigidbody`.

The owning client collects one input value per tick and simulates it immediately. The controlling worker simulates the same input and sends its result back. If the two positions differ by more than `CorrectionThreshold`, the client applies the worker state and repeats its later inputs. Nebula calls this process **reconciliation**.

## Define the input

Create a struct that implements `INetworkInput`. Implement `Serialize` and `Deserialize` in the same field order.

```csharp title="PlayerInput.cs"
using Nebula;
using UnityEngine;

public struct PlayerInput : INetworkInput
{
    public Vector2 Move;
    public float Yaw;
    public bool Jump;

    public void Serialize(NetworkWriter writer)
    {
        writer.WriteVector2(Move);
        writer.WriteFloat(Yaw);
        writer.WriteBool(Jump);
    }

    public void Deserialize(NetworkReader reader)
    {
        Move = reader.ReadVector2();
        Yaw = reader.ReadFloat();
        Jump = reader.ReadBool();
    }
}
```

Send player intent rather than the resulting transform. For example, send movement axes and a jump button instead of a world position. Keep the struct small because the client sends it every tick.

## Implement the predicted behavior

Derive the controller from `PredictedBehaviour<PlayerInput>`. Implement `GatherInput` and `Simulate`.

```csharp title="PlayerController.cs"
using Nebula;
using UnityEngine;
using UnityEngine.InputSystem;

public sealed class PlayerController : PredictedBehaviour<PlayerInput>
{
    public float Speed = 6f;
    private float _yaw;

    protected override PlayerInput GatherInput()
    {
        var keyboard = Keyboard.current;
        var move = Vector2.zero;
        if (keyboard != null)
        {
            move.x = (keyboard.dKey.isPressed ? 1f : 0f) -
                     (keyboard.aKey.isPressed ? 1f : 0f);
            move.y = (keyboard.wKey.isPressed ? 1f : 0f) -
                     (keyboard.sKey.isPressed ? 1f : 0f);
        }

        return new PlayerInput
        {
            Move = Vector2.ClampMagnitude(move, 1f),
            Yaw = _yaw,
            Jump = keyboard != null && keyboard.spaceKey.isPressed,
        };
    }

    protected override void Simulate(uint tick, in PlayerInput input, float deltaTime)
    {
        transform.rotation = Quaternion.Euler(0f, input.Yaw, 0f);
        var velocity =
            (transform.right * input.Move.x + transform.forward * input.Move.y) * Speed;
        transform.position += velocity * deltaTime;
        Identity.Motion.Velocity = velocity;
    }
}
```

Nebula calls `GatherInput` only on the owning client. It calls `Simulate` on the owning client, the authoritative worker, and again on the client during a replay.

Write `Simulate` as a deterministic update from the current state and input. Do not read live keyboard state, use `Time.deltaTime`, or make an unseeded random choice inside it. Use the supplied `deltaTime`.

Set `Identity.Motion.Velocity` when you move without a `NetworkRigidbody`. Remote interpolation and handover use this value.

## Handle one-time effects

A replay can call `Simulate` more than once for the same tick. Check `IsReplaying` before you play a sound, spawn a visual effect, or perform another effect that should happen only once.

Keep authoritative gameplay changes behind `HasAuthority`. The predicted client never has worker authority, even when it owns the entity.

For a fire button, store enough state in the input or controller to recognize one press. Consider using an increasing sequence number for an action that must survive a missing input packet. A repeated boolean can lose an edge when the worker repeats its previous input.

## Choose reconciliation state

By default, `WriteState` records the entity's container-local position and rotation plus `Identity.Motion.Velocity`. `ReadState` restores those values.

Override both methods when the next simulation result also depends on other state, such as grounded state, a movement mode, or a cooldown. Include everything `Simulate` carries from one tick to the next: the same state moves with the entity when another worker takes it over.

```csharp
protected override void WriteState(NetworkWriter writer)
{
    base.WriteState(writer);
    writer.WriteBool(_grounded);
    writer.WriteFloat(_cooldown);
}

protected override void ReadState(NetworkReader reader)
{
    base.ReadState(reader);
    _grounded = reader.ReadBool();
    _cooldown = reader.ReadFloat();
}
```

Read fields in the same order and with the same types used to write them. Call the base implementation first if you want to keep the default pose and velocity state.

Override `CorrectionThreshold` to change the position error that triggers a correction. The default is 0.05 meters. Use `OnCorrected(float magnitude)` for diagnostics or a visual response after a correction.

## Understand input timing

The client estimates the worker tick from snapshots and round-trip time. It sends input ahead by half the measured round-trip time, `InputLeadMarginTicks`, and an adaptive adjustment.

The worker reports the smallest lead it observed. The client tries to keep that value near `InputLeadTargetTicks`. It increases the adaptive adjustment when input arrives too late and slowly reduces it when the margin is larger than needed. Limit this adjustment with `InputLeadMaxAdjustTicks`.

If the expected input is missing, the worker repeats its most recent input instead of freezing the entity. It increments `InputsMissed`. If no input has arrived since spawn, it uses the default value of the input struct.

Use these values to diagnose timing:

- `PendingInputCount` is the number of future inputs buffered on the worker.
- `InputsMissed` counts ticks that repeated the previous input.
- `InputLeadMin` is the smallest lead observed during the reporting window.
- `LastProcessedInputTick` is the newest input tick the worker simulated.
- `ProcessedInputThisTick` reports whether the worker used a newly received input.

See [Debugging](/docs/guides/debugging#use-the-in-game-overlay) for the client-side lead values.

## Transfer prediction during handover

When an entity moves to another worker, the authority transfer includes the last processed input, future buffered inputs, the previous input used for repetition, and the state `WriteState` writes. The receiving worker applies that state with `ReadState`, so it continues on the next tick from exactly where the previous worker stopped, for example in the middle of a jump, without asking the client to resend its history.

The client keeps the same network ID and continues predicting. Owner-state messages from the new worker carry a higher authority epoch, so the client rejects older state from the previous worker.

If your simulation depends on state outside `WriteState`, `NetworkVariable`, or another replicated component, transfer it with `WriteHandoverState` and `ReadHandoverState`. See [Physics and handover state](/docs/guides/physics-and-handover-state).

## Drive an entity without a client

Call `NebulaWorker.SpawnServerDriven` to spawn an entity with no owning client. Override `GatherServerInput(uint tick)` to provide its input on the controlling worker.

```csharp
protected override PlayerInput GatherServerInput(uint tick)
{
    return new PlayerInput
    {
        Move = ChooseMovement(tick),
        Yaw = ChooseYaw(tick),
    };
}
```

The worker calls the same `Simulate` method used for a player. A server-driven entity can therefore move between workers through the normal handover path.

Store behavior state that must survive handover in a `NetworkVariable` or the handover-state methods. Rebuild worker-local state in `OnGainedAuthority`.

## Drive a vehicle

A vehicle that players drive, such as a car or a boat, is an entity no client owns: several players can ride in it, and it stays in the world when its driver leaves. Spawn it with `NebulaWorker.SpawnServerDriven` and give it a `PredictedBehaviour<TInput>`. When a player takes the driving seat, the worker hands that player's client the controls with `NetworkIdentity.SetDriver`. From then on the vehicle runs the driver's input on the worker, and the driver's client predicts it and reconciles it with the worker's state, as it does for its own pawn.

Without prediction, the driver sees the vehicle respond to the wheel a round trip plus about 110 ms later, because the worker's result reaches the client through the same interpolation delay as any other entity. On a 30 ms round-trip time (RTT) that is 140 ms; on a 150 ms RTT it is 273 ms, and a driver who steers by what they see turns past the heading they wanted. With prediction, the vehicle responds on the next frame at any latency. Other clients still see the vehicle interpolated.

### Write the vehicle

The vehicle's behavior is an ordinary predicted behavior. `GatherInput` reads the local player's controls, `GatherServerInput` says what the vehicle does with nobody at the wheel, and `Simulate` moves it.

```csharp title="VehicleController.cs"
using Nebula;
using UnityEngine;
using UnityEngine.InputSystem;

public struct VehicleInput : INetworkInput
{
    public float Throttle;
    public float Steer;

    public void Serialize(NetworkWriter writer)
    {
        writer.WriteFloat(Throttle);
        writer.WriteFloat(Steer);
    }

    public void Deserialize(NetworkReader reader)
    {
        Throttle = reader.ReadFloat();
        Steer = reader.ReadFloat();
    }
}

public sealed class VehicleController : PredictedBehaviour<VehicleInput>
{
    public float Acceleration = 8f;
    public float Drag = 0.4f;
    public float TurnRate = 60f;
    private float _speed;

    protected override VehicleInput GatherInput()
    {
        var keyboard = Keyboard.current;
        if (keyboard == null) return default;
        return new VehicleInput
        {
            Throttle = (keyboard.wKey.isPressed ? 1f : 0f) - (keyboard.sKey.isPressed ? 1f : 0f),
            Steer = (keyboard.dKey.isPressed ? 1f : 0f) - (keyboard.aKey.isPressed ? 1f : 0f),
        };
    }

    // Nobody at the wheel: coast to a stop.
    protected override VehicleInput GatherServerInput(uint tick) => default;

    protected override void Simulate(uint tick, in VehicleInput input, float deltaTime)
    {
        _speed += (input.Throttle * Acceleration - Drag * _speed) * deltaTime;
        float yaw = input.Steer * TurnRate * Mathf.Clamp01(Mathf.Abs(_speed) / 4f) * deltaTime;
        var rotation = Identity.LocalRotation * Quaternion.Euler(0f, yaw, 0f);
        var velocity = rotation * Vector3.forward * _speed;
        Identity.SetLocalPose(Identity.Container, Identity.LocalPosition + velocity * deltaTime, rotation);
        Identity.Motion.Velocity = Identity.Container != null ? Identity.Container.Rotation * velocity : velocity;
    }

    protected override void WriteState(NetworkWriter writer)
    {
        base.WriteState(writer);
        writer.WriteFloat(_speed);
    }

    protected override void ReadState(NetworkReader reader)
    {
        base.ReadState(reader);
        _speed = reader.ReadFloat();
    }
}
```

Keep `Simulate` deterministic and kinematic, as for a player controller: the client runs it again for a single vehicle during a replay, which PhysX cannot do for a `Rigidbody`. Do not use `NetworkRigidbody` or wheel colliders on a predicted vehicle. Write everything `Simulate` carries from tick to tick, such as the speed here, in `WriteState` and `ReadState`.

### Hand the controls to a player

Call `SetDriver` on the worker that has authority over the vehicle when a player's pawn takes the driving seat, and `ClearDriver` when it leaves:

```csharp
// On the worker, in your seat logic.
void OnDriverSeated(NetworkIdentity vehicle, NetworkIdentity pawn) => vehicle.SetDriver(pawn.OwnerClientId);

void OnDriverLeft(NetworkIdentity vehicle) => vehicle.ClearDriver();
```

`SetDriver` returns `false`, and logs a warning, when it is called on a copy without authority, on an entity with no predicted behavior, or on an entity a client owns: a player's pawn cannot be driven by anyone else. The vehicle has one driver at a time. Nebula announces the change to every client that holds the vehicle and carries it with the vehicle when another worker takes it over.

What each side does:

- The worker runs the driver's input every tick, even if the vehicle has a longer `UpdateInterval`, and sends the driver the vehicle's state. It ignores input for the vehicle from anybody else. A driven vehicle cannot sleep.
- The driver's client predicts the vehicle before its own pawn on each tick, so a pawn in the driving seat moves with the vehicle's new pose. `NebulaClient.DrivenEntities` lists what the client drives, and `NetworkBehaviour.IsDriver` is true on that client.
- Every copy of the behavior, on the worker and on each client, gets `OnDriverChanged(previous, current)`, with `0` for "nobody". Use it for cameras, prompts and HUDs.

### Seat the passengers

Put a `Container` on the vehicle's root so that it carries a box, and keep the driver's and passengers' pawns inside it: your pawn controller holds each pawn at its seat in the box's coordinates. Everything in the box moves with the vehicle, stays in its seat on every client, and changes worker with the vehicle. This also works when the vehicle itself is inside a moving container, such as a car in a ship's hold. See [Dynamic containers](/docs/guides/dynamic-containers) and [Physics frames](/docs/guides/physics-frames).

### Handle a driver who goes quiet or leaves

If the driver's input stops arriving, the worker repeats the last input for `DriverInputTimeoutTicks` (30 ticks, half a second), then runs `GatherServerInput` until the driver's input returns. The driver keeps the seat, so the vehicle does not stay at full throttle when a link drops. Override `DriverInputTimeoutTicks` to change the wait.

When the driver's session ends, for example because the player left, the worker that holds both the vehicle and the driver's pawn clears the driver. That is the usual case, since the pawn rides in the vehicle. A disconnected player who can still reconnect keeps the seat; to free it at once, call `ClearDriver` from `NebulaGameMode.OnPlayerDisconnected`.

### Know the limits

- Something only the worker knows about, such as another player's vehicle hitting yours, is corrected in one step by the size of the difference. Use `OnCorrected` if you want to ease that visually.
- A vehicle that needs PhysX to move cannot be predicted. It still works as a server-owned entity that the worker simulates and every client interpolates, with the delay described above.

## Perform a lag-compensated query

Each worker records a bounded window of recent ticks for every entity it holds, ghosts included. Call `NetworkIdentity.StateAt(tick)` to read the pose, velocity, container and marked variables at a tick, on the authority or on a ghost.

Use `NetworkTime.RenderTick` as the basis for the tick a client saw, and include that tick in the player's input when the worker must evaluate an action against past entity positions.

Nebula supplies the history but does not implement a complete hit-validation system. See [Lag compensation](/docs/guides/lag-compensation) for the window, the staleness bound, `[SyncHistory]` variables and the reference sample.

## Read correction diagnostics

Use these properties on `PredictedBehaviourBase`:

| Property | Meaning |
| --- | --- |
| `Corrections` | Number of client corrections since spawn or reset. |
| `LastCorrectionMagnitude` | Position error from the latest correction. |
| `MaxCorrectionMagnitude` | Largest correction since spawn or `ResetCorrectionStats`. |

Use `NebulaClient.RttMs`, `InputLeadTicks`, `InputLeadAdjustTicks`, `LastReportedInputLead`, and `InputLeadIncreases` to inspect the network timing that affects prediction.
