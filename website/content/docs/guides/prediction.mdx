---
title: Prediction and reconciliation
description: Predict an owned entity, reconcile it with worker state, drive server-owned entities, and perform lag-compensated queries.
---

Use `PredictedBehaviour<TInput>` for an entity that must respond to local input before a worker reply arrives. A player controller is the common example.

The owning client collects one input value per tick and simulates it immediately. The controlling worker simulates the same input and sends its result back. If the two positions differ by more than `CorrectionThreshold`, the client applies the worker state and repeats its later inputs. Nebula calls this process **reconciliation**.

## Define the input

Create a struct that implements `INetworkInput`. Implement `Serialize` and `Deserialize` in the same field order.

```csharp title="PlayerInput.cs"
using Nebula;
using UnityEngine;

public struct PlayerInput : INetworkInput
{
    public Vector2 Move;
    public float Yaw;
    public bool Jump;

    public void Serialize(NetworkWriter writer)
    {
        writer.WriteVector2(Move);
        writer.WriteFloat(Yaw);
        writer.WriteBool(Jump);
    }

    public void Deserialize(NetworkReader reader)
    {
        Move = reader.ReadVector2();
        Yaw = reader.ReadFloat();
        Jump = reader.ReadBool();
    }
}
```

Send player intent rather than the resulting transform. For example, send movement axes and a jump button instead of a world position. Keep the struct small because the client sends it every tick.

## Implement the predicted behavior

Derive the controller from `PredictedBehaviour<PlayerInput>`. Implement `GatherInput` and `Simulate`.

```csharp title="PlayerController.cs"
using Nebula;
using UnityEngine;
using UnityEngine.InputSystem;

public sealed class PlayerController : PredictedBehaviour<PlayerInput>
{
    public float Speed = 6f;
    private float _yaw;

    protected override PlayerInput GatherInput()
    {
        var keyboard = Keyboard.current;
        var move = Vector2.zero;
        if (keyboard != null)
        {
            move.x = (keyboard.dKey.isPressed ? 1f : 0f) -
                     (keyboard.aKey.isPressed ? 1f : 0f);
            move.y = (keyboard.wKey.isPressed ? 1f : 0f) -
                     (keyboard.sKey.isPressed ? 1f : 0f);
        }

        return new PlayerInput
        {
            Move = Vector2.ClampMagnitude(move, 1f),
            Yaw = _yaw,
            Jump = keyboard != null && keyboard.spaceKey.isPressed,
        };
    }

    protected override void Simulate(uint tick, in PlayerInput input, float deltaTime)
    {
        transform.rotation = Quaternion.Euler(0f, input.Yaw, 0f);
        var velocity =
            (transform.right * input.Move.x + transform.forward * input.Move.y) * Speed;
        transform.position += velocity * deltaTime;
        Identity.Motion.Velocity = velocity;
    }
}
```

Nebula calls `GatherInput` only on the owning client. It calls `Simulate` on the owning client, the authoritative worker, and again on the client during a replay.

Write `Simulate` as a deterministic update from the current state and input. Do not read live keyboard state, use `Time.deltaTime`, or make an unseeded random choice inside it. Use the supplied `deltaTime`.

Set `Identity.Motion.Velocity` when you move without a `NetworkRigidbody`. Remote interpolation and handover use this value.

## Handle one-time effects

A replay can call `Simulate` more than once for the same tick. Check `IsReplaying` before you play a sound, spawn a visual effect, or perform another effect that should happen only once.

Keep authoritative gameplay changes behind `HasAuthority`. The predicted client never has worker authority, even when it owns the entity.

For a fire button, store enough state in the input or controller to recognize one press. Consider using an increasing sequence number for an action that must survive a missing input packet. A repeated boolean can lose an edge when the worker repeats its previous input.

## Choose reconciliation state

By default, `WriteState` records the entity's container-local position and rotation plus `Identity.Motion.Velocity`. `ReadState` restores those values.

Override both methods when the next simulation result also depends on other state, such as grounded state, a movement mode, or a cooldown.

```csharp
protected override void WriteState(NetworkWriter writer)
{
    base.WriteState(writer);
    writer.WriteBool(_grounded);
    writer.WriteFloat(_cooldown);
}

protected override void ReadState(NetworkReader reader)
{
    base.ReadState(reader);
    _grounded = reader.ReadBool();
    _cooldown = reader.ReadFloat();
}
```

Read fields in the same order and with the same types used to write them. Call the base implementation first if you want to keep the default pose and velocity state.

Override `CorrectionThreshold` to change the position error that triggers a correction. The default is 0.05 meters. Use `OnCorrected(float magnitude)` for diagnostics or a visual response after a correction.

## Understand input timing

The client estimates the worker tick from snapshots and round-trip time. It sends input ahead by half the measured round-trip time, `InputLeadMarginTicks`, and an adaptive adjustment.

The worker reports the smallest lead it observed. The client tries to keep that value near `InputLeadTargetTicks`. It increases the adaptive adjustment when input arrives too late and slowly reduces it when the margin is larger than needed. Limit this adjustment with `InputLeadMaxAdjustTicks`.

If the expected input is missing, the worker repeats its most recent input instead of freezing the entity. It increments `InputsMissed`. If no input has arrived since spawn, it uses the default value of the input struct.

Use these values to diagnose timing:

- `PendingInputCount` is the number of future inputs buffered on the worker.
- `InputsMissed` counts ticks that repeated the previous input.
- `InputLeadMin` is the smallest lead observed during the reporting window.
- `LastProcessedInputTick` is the newest input tick the worker simulated.
- `ProcessedInputThisTick` reports whether the worker used a newly received input.

See [Debugging](/docs/guides/debugging#use-the-in-game-overlay) for the client-side lead values.

## Transfer prediction during handover

When an entity moves to another worker, the authority transfer includes the last processed input, future buffered inputs, and the previous input used for repetition. The receiving worker can therefore continue on the next tick without asking the client to resend its history.

The client keeps the same network ID and continues predicting. Owner-state messages from the new worker carry a higher authority epoch, so the client rejects older state from the previous worker.

If your simulation depends on state outside `WriteState`, `NetworkVariable`, or another replicated component, transfer it with `WriteHandoverState` and `ReadHandoverState`. See [Physics and handover state](/docs/guides/physics-and-handover-state).

## Drive an entity without a client

Call `NebulaWorker.SpawnServerDriven` to spawn an entity with no owning client. Override `GatherServerInput(uint tick)` to provide its input on the controlling worker.

```csharp
protected override PlayerInput GatherServerInput(uint tick)
{
    return new PlayerInput
    {
        Move = ChooseMovement(tick),
        Yaw = ChooseYaw(tick),
    };
}
```

The worker calls the same `Simulate` method used for a player. A server-driven entity can therefore move between workers through the normal handover path.

Store behavior state that must survive handover in a `NetworkVariable` or the handover-state methods. Rebuild worker-local state in `OnGainedAuthority`.

## Perform a lag-compensated query

Each worker records about one second of poses for its resident entities, including ghosts. Call `NetworkIdentity.TryGetPoseAt(tick, out position, out rotation)` to retrieve the pose for a tick. When that exact tick is unavailable, the method can return the nearest later pose within a small window.

Use `NetworkTime.RenderTick` as the basis for the tick a client saw. Include that tick in the player's input when the worker must evaluate an action against past entity positions.

Nebula supplies pose history but does not implement a complete hit-validation system. Your game must decide which entities and containers to query, how to move colliders temporarily, and how to validate results from another worker. Restore every changed transform before you continue simulation.

## Read correction diagnostics

Use these properties on `PredictedBehaviourBase`:

| Property | Meaning |
| --- | --- |
| `Corrections` | Number of client corrections since spawn or reset. |
| `LastCorrectionMagnitude` | Position error from the latest correction. |
| `MaxCorrectionMagnitude` | Largest correction since spawn or `ResetCorrectionStats`. |

Use `NebulaClient.RttMs`, `InputLeadTicks`, `InputLeadAdjustTicks`, `LastReportedInputLead`, and `InputLeadIncreases` to inspect the network timing that affects prediction.
