title: Manage workers and containers
description: Use the orchestrator, Nebula Dashboard, and HTTP API to inspect and resize a running mesh.
---

Use the **orchestrator** to keep the requested number of workers running and distribute containers between them. The orchestrator does not simulate gameplay. Workers communicate directly with the gateway and with each other during normal simulation.

Start the orchestrator with `-nebula-role orchestrator`. The `nebula start` and `nebula deploy` commands supply this option for you.

## Understand container assignment

The orchestrator stores each container assignment as a **lease** in the control plane. A lease names the worker that currently controls the container. Its **epoch** is a number that increases whenever the assignment changes, which lets workers reject an older assignment.

Every 500 milliseconds, the orchestrator:

1. Reports its own heartbeat.
2. Checks worker heartbeats and removes dead workers.
3. Starts or retires workers until the requested count is reached.
4. Distributes containers as evenly as possible.
5. Publishes a current state snapshot for the dashboard.

Nebula keeps a container on its current live worker when that worker remains within its even share. This reduces container movement during a resize.

For example, four workers and four containers results in one container per worker. With three workers, one worker receives two containers. With one worker, that worker receives every container.

## Change the worker count

Set the initial count in `NebulaConfig.WorkerCount`, with `-nebula-workers`, or in `nebula.json`. After the mesh starts, use the dashboard or HTTP API to change it. Nebula supports up to 32 workers.

When you add a worker, the orchestrator starts it on the lowest available worker index and rebalances containers.

When you remove a worker, the orchestrator retires the highest-index worker by default. It first assigns the worker's containers to other workers. The retiring worker then transfers its authoritative entities through the normal handover process.

The orchestrator stops the retiring worker after it has no containers or authoritative entities. It stops the worker after `WorkerDrainTimeoutSeconds` even if the drain has not completed. If you scale to zero, no worker can receive the entities, so every retiring worker stops after the timeout.

## Handle a failed worker

Each worker writes a heartbeat to the control plane. When a heartbeat is older than `WorkerTimeoutSeconds`, the orchestrator treats the worker as dead and assigns its containers to surviving workers.

After `DeadWorkerReplaceDelaySeconds`, the orchestrator starts a replacement on the same worker index. It can react sooner when the worker process exits or its cloud VM disappears.

<Callout type="warn" title="Transient state is not restored">
Nebula does not persist entity state. Entities controlled only by a failed worker are lost. The gateway asks the new container owner to spawn affected players again.
</Callout>

## Open the Nebula Dashboard

To open the local dashboard, visit `http://localhost:7080/`. Change `NebulaConfig.DashboardPort` or pass `-nebula-dashboard-port` to use another port. Set the port to `0` to disable the dashboard.

The dashboard binds to `localhost` by default. Pass `-nebula-dashboard-bind +` to listen on every interface, or pass one address to listen only on that interface.

<Callout type="warn" title="Restrict dashboard access">
The dashboard and its HTTP API do not require authentication. When you expose the port outside your computer, use a firewall to allow only trusted addresses.
</Callout>

Use the overview to:

- Check live and requested worker counts.
- See which worker controls each container.
- Compare authoritative and ghost entity counts.
- Review player, bot, and server-driven entity counts.
- Check tick time and heartbeat age for each worker.
- Add, retire, or stop a worker.
- Edit game-defined mesh settings.
- Pin a dynamic container to a worker or return it to its carrier's worker.
- Read recent orchestrator events.

Stopping a worker with **Kill** simulates a crash. The orchestrator reassigns its containers and starts a replacement. Removing a worker performs a graceful drain and reduces the requested worker count.

## Inspect the world map

Open `/map` from the dashboard to see the mesh from above. The map shows:

- Static and world-partition cell containers.
- The worker that controls each container.
- Dynamic containers and their carriers.
- Authoritative entities and ghost copies.
- Loaded world cells and container boundaries.

Drag to pan, scroll to zoom, and select an item to inspect it. Use the side controls to switch between worker ownership and entity load or to hide individual layers.

Workers send summary telemetry once per second. While someone has the map open, workers send detailed entity positions every half second, up to 4,096 authoritative entities per worker. Pass `-nebula-telemetry off` to a manually started worker to disable this telemetry.

## Edit persisted records

Open `/persistence` from the dashboard to see everything the persistence store holds. The tab is empty when persistence is off. It groups records as a tree: containers first, then the entities saved in each container, with entities carried inside another entity nested under their carrier. Badges mark a record that a client owned, a server-driven entity, a scene object, and a record this build cannot decode.

Select a record to inspect it. The editor shows its identity as read-only text (key, prefab or scene ID, epoch, version, and when and by which worker it was saved), then editable fields for its name, container ID, position, rotation, and velocity, then one row per saved state entry.

The orchestrator runs the same build as the workers, so it can decode the saved state. It resolves the record's prefab or scene object, matches each entry against that object's `NetworkVariable` fields by name, and reads the bytes with the field's type. Booleans, numbers, strings, enumerations, vectors, quaternions, and colors get a matching control. Anything else appears as hexadecimal bytes that you can still replace: the state a behavior writes in `WritePersistentState`, an entry whose variable this build no longer has, and a value type Nebula cannot edit. Saving rewrites only the entries you changed and keeps the other bytes as they were.

Use **Duplicate as…** with a new key to copy a record, for example to place a second object. Use **Delete** to remove one record, or **Clear persistence** on the overview to remove every record.

<Callout type="warn" title="Edit records of entities that are not running">
An edit is written to the store, not to a running worker. A worker that is currently simulating the entity overwrites your edit at its next checkpoint. Edit a record while the mesh is stopped, after the entity was deleted, or restrict your edit to fields the entity never writes back.
</Callout>

## Use the HTTP API

The dashboard and API use the same port. Read `/api/state` to get the latest orchestrator snapshot.

```powershell
Invoke-RestMethod http://localhost:7080/api/state | Select-Object desiredWorkers, totals
```

Send JSON with `Content-Type: application/json` for operations that change the mesh:

```powershell
Invoke-RestMethod -Method Post http://localhost:7080/api/desired -ContentType application/json -Body '{"desired": 2}'
Invoke-RestMethod -Method Post http://localhost:7080/api/workers/kill -ContentType application/json -Body '{"workerId": "w3"}'
```

| Method and path | Body | Result |
| --- | --- | --- |
| `GET /api/state` | none | Returns workers, containers, gateways, totals, settings, and recent events. |
| `POST /api/desired` | `{"desired": 2}` | Sets the requested worker count between 0 and 32. |
| `POST /api/settings` | `{"key": "round-time", "value": "600"}` | Sets one game-defined mesh setting. |
| `POST /api/workers/add` | none | Adds one to the requested worker count. |
| `POST /api/workers/remove` | `{"workerId": "w3"}` or `{}` | Gracefully retires one worker. Without an ID, Nebula chooses the highest index. |
| `POST /api/workers/kill` | `{"workerId": "w3"}` | Stops one worker immediately to simulate a failure. |
| `POST /api/rebalance` | none | Runs a container-assignment pass immediately. |
| `POST /api/containers/pin` | `{"containerId": "interior#…", "workerId": "w2"}` | Assigns a dynamic container to a live worker. |
| `POST /api/containers/unpin` | `{"containerId": "interior#…"}` | Returns a dynamic container to its carrier's worker. |
| `GET /api/persistence/records` | none | Returns every persisted record with its state decoded into named entries. |
| `POST /api/persistence/record` | `{"key": "…", "position": [x, y, z], "entries": {"Box.Stack": "9"}}` | Saves one record. Send only the fields and entries you change. |
| `POST /api/persistence/duplicate` | `{"key": "…", "newKey": "…"}` | Copies one record under a new key. |
| `POST /api/persistence/delete` | `{"key": "…"}` | Deletes one record. |
| `POST /api/persistence/clear` | none | Deletes every persisted record. |
| `GET /api/map/geometry` | none | Returns static world and container geometry. |
| `GET /api/map` | none | Returns the latest worker telemetry. |

Successful changes return `{"ok":true}`. Invalid requests return an error message. An API write can return `503` when it cannot reach the orchestrator's main thread within three seconds.

## Choose where workers run

Set `NebulaConfig.WorkerHost` or pass `-nebula-host` to select a worker host:

| Value | Where workers run | When to use it |
| --- | --- | --- |
| `process` | Child processes on the orchestrator's computer | Use for local development. This is the default used by `nebula start`. |
| `hetzner` | One Hetzner Cloud VM per worker | Use for hosted tests. This is the host used by `nebula deploy`. |

The gateway always runs as a child process next to the orchestrator, even when workers run on cloud VMs.

For a local process host, set `NebulaConfig.WorkerExecutable` or pass `-nebula-worker-exe` when the orchestrator cannot find the game executable. Worker logs are written to the build's `Logs` directory.

For Hetzner, let `nebula deploy` configure the private network, VM image, firewall, SSH key, build URL, and API token. See [Deploy to Hetzner Cloud](/docs/deploy/hetzner).

## Test simulation load

Start a bot to test the complete client path:

```bash
nebula start --bots 2
```

A bot is a headless client process. Your game must provide its input behavior. Each bot runs a complete Unity player, so start only as many as you need.

Use `NebulaWorker.SpawnServerDriven` to test worker simulation without another client process. Your game must provide the entity's behavior and spawning policy.
