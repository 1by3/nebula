title: Connecting clients
description: Let players choose a gateway with the optional NebulaTitleScreen, or connect from your own UI with NebulaClient.ConnectTo.
---

To let a player join a mesh, connect the client to the gateway. The gateway is the process that accepts client connections. Nebula does not show a connection screen unless you add one. Choose one of these options:

| Option | Use it when |
| --- | --- |
| Add `NebulaTitleScreen` | You want a working connection screen during development. |
| Call `NebulaClient.ConnectTo` from your own UI | You want the connection flow to match your game. |
| Pass connection arguments on the command line | You start bots, test clients, or clients from a launcher. |

## Use the title screen

Add [`NebulaTitleScreen`](/docs/reference/client/nebula-title-screen) to the same GameObject as `NebulaBootstrap`. **Nebula > Set Up Active Scene** adds it for you.

The title screen asks for the gateway address and a display name. It saves both values in `PlayerPrefs` and fills them in the next time the game starts. After the local player spawns, the title screen hides. Press Escape to show it again, disconnect, or choose another gateway.

The title screen stays hidden in processes without the client role. It also stays hidden when the client connects on its own at startup.

<Callout type="warn" title="Keep the title screen on the bootstrap object">
The bootstrap keeps its GameObject when it loads the game scene. If your boot scene differs from `NebulaConfig.GameScene`, a title screen on another object in the boot scene is destroyed when the game scene loads.
</Callout>

## Connect from your own UI

Remove `NebulaTitleScreen` or leave it out of the scene. A client started without connection arguments then stays idle until your code connects it.

Get the client from `NebulaBootstrap.Instance.Client`. The bootstrap creates the client after the game scene loads, so check for `null` before you use it.

```csharp title="ConnectMenu.cs"
using Nebula;
using UnityEngine;

public sealed class ConnectMenu : MonoBehaviour
{
    public string GatewayAddress = "127.0.0.1";
    public ushort GatewayPort = 7000;
    public string PlayerName = "Player";

    // Call this from your Connect button.
    public void Connect()
    {
        var client = NebulaBootstrap.Instance != null ? NebulaBootstrap.Instance.Client : null;
        if (client == null) return; // The client role has not started yet.
        client.ConnectTo(GatewayAddress, GatewayPort, PlayerName);
    }
}
```

`ConnectTo` replaces the configured gateway address and retries connection failures every 2 seconds until it connects, receives a refusal that stops automatic retries, or you call `Disconnect`. A blank player name keeps the current name, which comes from `-nebula-name` or the operating system user name (`player` in a web build).

The gateway also identifies the player when it connects: anonymously by default, or from an OpenID Connect token you set in `NebulaClient.AuthToken` before connecting. See [Authentication and player identity](/docs/guides/authentication).

Use these `NebulaClient` members to drive your UI:

| Member | Use it to |
| --- | --- |
| `ConnectionState` and `ConnectionStateChanged` | Show `Disconnected`, `Connecting`, `Connected`, or `InGame`. |
| `Join`, `JoinEstimatedSeconds` and `JoinStateChanged` | Show a "world starting" screen while the mesh boots a worker (see below). |
| `LocalPlayer` and `LocalPlayerSpawned` | Hide your menu when the player's entity arrives. |
| `ClientId` | Read the local session ID, a `ulong` the gateway assigned in its welcome. `NebulaRuntime.LocalClientId` holds the same value. It is `0` before the welcome. |
| `Identity` | Read the player's identity across sessions (see [Authentication](/docs/guides/authentication)). |
| `SessionToken` and `SessionReclaimed` | Keep or drop the session across reconnections (see below). |
| `JoinRejected` | Show why the gateway refused the join. |
| `GatewayDraining` | Tell the player that the client is switching gateways (see below). |
| `LastError` | Show why the last connection attempt failed or ended. It is empty while the connection is healthy. |
| `WantsConnection` | Tell whether the client is connecting or will retry. |
| `ConnectsAutomatically` | Hide your menu when the command line already supplied the connection. |
| `Disconnect()` | Leave the gateway and stop retrying. |

### The "world starting" state

A mesh with [scale to zero](/docs/guides/orchestrator-and-dashboard#scale-to-zero) turned on (`MinWorkers = 0`) keeps no workers while nobody is playing. A client that joins then is welcomed normally, but there is nowhere to spawn it yet, so the gateway holds the join instead of rejecting it: `Join` becomes `JoinState.Starting` and `JoinEstimatedSeconds` is roughly how long a worker takes to boot on that host. When the worker is up the gateway places the player, `Join` becomes `JoinState.Joined` and `LocalPlayer` arrives - all on the same connection, with no reconnect and nothing for your UI to retry.

```csharp
client.JoinStateChanged += (state, seconds) =>
{
    StartingPanel.SetActive(state == JoinState.Starting);
    StartingLabel.text = seconds > 0 ? $"World starting, about {seconds} s..." : "World starting...";
};
```

`NebulaTitleScreen` already does this: it shows "world starting, about 75 s..." in place of "waiting for a pawn...".

`NebulaTitleScreen.TryParse` splits text such as `127.0.0.1:7000` into an address and port. You can use it to validate a single address field.

### Reconnect after a lost link or a draining gateway

The client keeps its **session** across a reconnection. The gateway's welcome carries a session token, which the client stores in `NebulaClient.SessionToken` and presents on every later connection. A gateway that verifies it, any gateway of the mesh, welcomes the client with the same `ClientId` and, when the worker still holds the pawn, the same pawn; `SessionReclaimed` is then `true`. See [Sessions and reconnection](/docs/guides/authentication#sessions-and-reconnection) for what the token does and does not guarantee.

The client handles these connection events automatically:

- **The link drops.** `ConnectionState` becomes `Disconnected`, `LastError` reads `disconnected from gateway (retrying)`, and the client reconnects to the same address after one second, then every two seconds, until it succeeds or you call `Disconnect()`. The worker keeps the pawn for `NebulaConfig.SessionReclaimSeconds` (default 30 s); a player who comes back within that time continues with it.
- **This player connected again somewhere else.** The gateway sends `SessionReplaced`, the `SessionReplaced` event fires with a reason fit to show the player, and the client leaves the world and stays out: the newer connection has the player's session and pawn. Reconnect only when the player asks to, which takes the player back. See [One connection per player](/docs/guides/authentication#one-connection-per-player).
- **The gateway is being taken out of service.** The gateway sends `GatewayDraining` with the number of seconds it gives its clients, the `GatewayDraining` event fires with that number, and the client drops the link and reconnects at once with its session token. When the gateway address is a load balancer, the retry lands on another gateway; when it is one gateway, the client keeps retrying until that gateway is back in service. A gateway that is draining refuses a new join with the reason `gateway is draining`; the client retries after a second instead of giving up.

If a gateway process fails, session coordination can reclaim its sessions after its heartbeat exceeds the configured `WorkerTimeoutSeconds` (default 5 s). Reclaim time also depends on failure detection, retries, network delays, and control-plane availability. Tests with default settings use a 9-second threshold measured from a reconnect attempt reaching a live gateway; this is not a deployment guarantee. See [the scale suite](/docs/guides/scale-suite).

The client retries its configured `GatewayAddress`. Nebula does not provide a load balancer: configure your address and infrastructure so a retry can reach a surviving gateway. If the address still points only to the failed gateway, the session cannot be reclaimed there.

The replicated world is cleared on every reconnection and replayed by the gateway that answers, so entities disappear for a moment and `LocalPlayerSpawned` fires again. Show a short "reconnecting" message from `ConnectionStateChanged` or `GatewayDraining` rather than returning to your main menu.

To start a new session on purpose, for example when the player picks another character, clear `SessionToken` before connecting. `Disconnect()` keeps it, so a deliberate disconnect and reconnect continues the session.

## Connect from the command line

A client connects to the gateway at startup when you pass one of these options:

- `-nebula-gateway <address:port>` connects to that gateway. Replace `<address:port>` with the gateway's address, such as `127.0.0.1:7000`.
- `-nebula-connect` connects to `NebulaConfig.GatewayAddress` and `GatewayPort`.
- `-nebula-bot` starts a bot client, which connects to the configured gateway.

```bash
Builds\Win64\Nebula.exe -nebula-role client -nebula-gateway 127.0.0.1:7000 -nebula-name Player
```

For these clients, `ConnectsAutomatically` is `true`. See [Configuration](/docs/guides/configuration#override-runtime-values-on-the-command-line) for every runtime option.

## Connect from a web build

A web build connects to the gateway over WebRTC and reads the same options from the page's query string, such as `?nebula-name=Player&nebula-connect`. By default it connects to the gateway that served the page. See [Build for the web](/docs/guides/web-builds).

<Callout type="warn" title="UDP connections are not encrypted by default">
A native client's UDP link is encrypted only when you turn it on. See [Encrypt client connections](/docs/deploy/encryption). By default anyone who can reach the gateway address can join with an anonymous identity; to require a sign-in, see [Authentication](/docs/guides/authentication).
</Callout>
