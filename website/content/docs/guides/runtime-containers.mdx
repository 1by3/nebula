title: Runtime containers
description: Register containers while the mesh runs, so a world whose shape is decided by the game (a chunked landscape, player plots) is simulated across workers without a baked manifest.
---

Use a **runtime container** when the game decides where the containers are while the mesh runs. A chunked landscape that grows as players explore it, plots that appear when someone buys land, or an instance that exists while a group is inside are all runtime containers. Baked containers (authored in the scene or in a world manifest) and dynamic containers (carried by an entity) keep working alongside them.

For a chunked landscape specifically, `NebulaConfig.ChunkedWorld` builds and balances runtime containers for you — see [Build an infinite runtime world](/docs/guides/infinite-runtime-world) for that path, built on the API this page describes. Use this page directly when your game's containers are not a uniform chunk grid, or you need more control than `NebulaChunks` gives you.

A client only learns about a runtime container that overlaps a [`NearCells` window](/docs/guides/interest-management#scoped-container-ownership) around one of the client's authorized foci (its pawn by default; every focus with a free camera or a policy), its current instance, or a dynamic container carrying an entity already in its interest set — not every runtime container the mesh has registered. `ContainerRegistry.Runtime` and the events below still enumerate every registered container on a worker or the orchestrator, which see the whole mesh regardless of any one client's interest set.

A runtime container is a static box named by a 64-bit id the game chooses. Its lease row on the control plane carries the box, so every process registers the same container from the row alone; nothing about the world's shape is baked into a build. On the wire it is ten bytes (a marker index plus the id), where a baked container is two. Baked containers are unaffected.

To create separate private copies with isolated visibility and physics, follow [Create private instances](/docs/guides/instancing). An ordinary runtime container remains in the public scope unless it carries instance metadata.

## Ask for a container

On a worker, ask for a container next to the entities that need it. The request is idempotent, so call it every time an entity comes near the box:

```csharp
ulong id = Chunks.IdOf(coord);            // your hash of the chunk coordinate
Bounds box = Chunks.BoundsOf(coord);     // in this process's frame
worker.RequestRuntimeContainer(id, box);
```

An overload takes a [balancing hint](#balancing-hints) alongside the box, so a chunk that holds a boss arena can say so as it is created:

```csharp
worker.RequestRuntimeContainer(id, box, new ContainerHint { Dedicated = true });
```

The lease row is created already assigned to the requesting worker, so the container is simulated there from the first change anyone sees. If another worker asked first, its row stands and the call is a no-op. The orchestrator can move the container later.

The gateway, the orchestrator, every worker and every client mirror the lease rows into their `ContainerRegistry` (`ContainerRegistry.Runtime`), and `ContainerRegistry.RuntimeRegistered` fires on each process once the box is there. Load whatever content belongs in the box from that event: terrain and colliders on workers, visuals on clients.

```csharp
ContainerRegistry.RuntimeRegistered += container =>
{
    var coord = Chunks.CoordOf(container.RuntimeId);
    LoadTerrain(coord, container.transform);
};
ContainerRegistry.RuntimeUnregistering += container => UnloadTerrain(Chunks.CoordOf(container.RuntimeId));
```

Entities inside a runtime container are spawned, handed over and ghosted exactly like in a baked one. Adjacency is computed when the box registers, against baked and runtime containers whose boxes touch it, so the ghost band and handover across a chunk seam work without any extra setup.

## Balancing hints

The orchestrator measures how busy each worker is, but it cannot know what a container *means*. A hint tells it what the game knows. Every field is optional and the default says nothing:

| Field | Effect |
| --- | --- |
| `CostMultiplier` | Scales what the planner treats the container as costing. `1` is "as measured"; `2` gives it twice the room. The correction for a container whose occupant count is a poor proxy for its tick time. |
| `AffinityGroup` | Containers sharing a non-empty group are dealt as a single item, so they land on one worker. |
| `SeamCost` | `0..1`. Where two neighbors both carry it, the planner is charged for cutting between them and prefers to cut elsewhere. |
| `Dedicated` | Reserves a worker for this container before dealing the rest. A worker holding one is never chosen for retirement. |

Worked examples:

- **A city hub.** One cell everybody passes through. Mark it `Dedicated` and it gets a machine to itself; the rest of the map is dealt across what is left.
- **A battle royale.** Raise `SeamCost` on the cells inside the circle at the start of each phase, and the worker boundary moves out of the fight instead of running through it.
- **An instanced dungeon.** Give the rooms of one instance a shared `AffinityGroup` so a party never crosses a machine boundary walking through a door.
- **A chunked world with nothing special in it.** Leave everything default; the measured signal is enough.

Set a hint at bake time (the World window, stored in the manifest), at runtime from game code, or from the dashboard. The runtime value wins over the baked one, and it lives on the container's control-plane row, so an orchestrator restart still sees it.

```csharp
// From game code on a worker, in the same call that asks for the container.
worker.RequestRuntimeContainer(id, box, new ContainerHint { Dedicated = true });

// Or at any time, for any container.
orchestrator.SetContainerHint("cell_3_0_1", new ContainerHint { CostMultiplier = 2f, SeamCost = 0.5f });
```

The compact form used by the dashboard and the HTTP API is `x2,group=keep,seam=0.5,dedicated`; an empty string clears the runtime hint and lets the baked one stand again.

If more containers ask to be `Dedicated` than the mesh has workers to spare (it needs one more worker than there are dedicated containers), none of them is reserved and they share like anything else. The orchestrator logs it and the dashboard shows the reason above the container list.

## Retire a container

The owning worker retires a container when nobody needs it any more:

```csharp
worker.ReleaseRuntimeContainer(id);
```

Persistent entities still inside are checkpointed and despawned; anything else inside is despawned for good. The lease row is deleted and every process forgets the box. When the container is asked for again, Nebula's persistence restores the entities that were saved in it: a persisted entity's record names its container by id (`rt_<id>`), so the props of a chunk come back with the chunk.

Entities riding in a vehicle in the container, at any depth, leave with the vehicle. Nebula despawns them before the vehicle and saves each persistent one aboard it, so it comes back with the vehicle. See [Dynamic containers](/docs/guides/dynamic-containers#handle-container-removal).

Only the owner can release. Before retiring, read `worker.RuntimeContainerIdleSeconds(id)`: every worker that still wants the box re-stamps its lease row while an entity of its is near it, so the row's age is the mesh-wide idle time. A clock of the owner's own would retire a chunk the neighbor's pawn is about to enter, and its props would blink out and back.

Entities inside a container that goes away are detached from it, never destroyed with it: ghosts on a worker and every remote entity on a client stay alive and pick up the next container from the following state update.

## Assignment policy

Runtime containers are dealt to workers by the orchestrator's assignment policy (`NebulaConfig.AssignmentPolicy`, or `-nebula-assignment`):

| Policy | Behaviour |
| --- | --- |
| `baked` | The opt-out for games that want count-based sticky dealing: baked containers evenly by count, sticky to their owner. Runtime containers stay with the worker that asked for them and only move when it is gone. |
| `cost` | Every container costs what its occupants cost (`NebulaConfig.CostWeights`: a leased box, a player, a bot, a server-driven entity). Containers are ordered along a Morton curve of their centres and cut into one contiguous run of roughly equal cost per worker. Nothing moves while the most loaded worker is within `CostRebalanceThreshold` of the average. |
| `auto` | The default: `cost`, for baked and runtime worlds alike. |

Occupancy comes from the telemetry workers already post to the dashboard once a second. A game may install its own policy by assigning `NebulaOrchestrator.Policy`; the input it receives is the baked and runtime containers, the eligible workers, the leases and the per-container occupancy.

The cost policy also refuses to re-deal when the move would buy less than `ScaleMinGain` of a tick on the busiest worker: a handover costs entity transfers and a visible seam, so it has to be worth making.

`NebulaConfig.AutoScale` is on by default and keeps the worker count between `MinWorkers` and `MaxWorkers` from the tick time workers report, checking every change against a dry run of this policy first. See [Autoscale](/docs/guides/orchestrator-and-dashboard#autoscale). Launching goes through the configured worker host, so a Hetzner mesh gets a new machine.

## Tooling

The dashboard's state lists runtime containers with the baked ones and shows the policy in use. The World map draws their boxes. `POST /api/containers/ensure` with `{"id": 5, "center": [x, y, z], "size": [x, y, z]}` creates a container from outside the game, and `POST /api/containers/remove` with `{"id": 5}` retires one.

## Limits

- Boxes are axis-aligned in absolute world coordinates. With a partitioned world's floating origin active they are brought into each process's frame and shifted with it.
- The lease table gained columns for the box. Publish the control-plane module again after upgrading (`nebula start` does; `nebula deploy --reset-control-plane` for a cloud mesh).
- A world with no baked containers has nowhere to put the first player until a worker asks for a container. Allocate the chunks around the spawn point from `NebulaGameMode.OnWorkerStarted`.
