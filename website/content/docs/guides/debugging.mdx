Start a debugging session by identifying the process that owns the failing operation. Use the client overlay for prediction and connection problems. Use worker logs for simulation and handover problems. Use the gateway log for routing problems. Use the orchestrator log and dashboard for worker lifecycle and container-assignment problems.

Nebula prefixes its log messages with `[nebula]` so you can filter them in Unity logs.

## Use the in-game overlay

Add [`NebulaDebugOverlay`](/docs/reference/debug/nebula-debug-overlay) to the same GameObject as `NebulaBootstrap`. **Nebula > Set Up Active Scene** adds it for you.

The overlay displays a block for each role in the current process:

| Role | Information |
| --- | --- |
| Client | Connection state, round-trip time (RTT), estimated server tick, prediction tick, input lead, entity count, authority changes, and prediction corrections. |
| Worker | Worker ID, tick, tick time, authoritative and ghost counts, player and bot counts, server-driven count, and handover totals. |
| Gateway | Connected clients, connected workers, and tracked entities. |
| Orchestrator | Requested workers, rebalances, and dashboard address. |
| Containers | The worker and lease epoch for each container. |

When local movement feels wrong, compare these client values:

- `lead` is the number of ticks the client runs ahead of its estimated worker tick.
- `adaptive` is the extra lead added because input arrived late.
- `worker sees` is the latest input lead reported by the worker.
- `corrections` counts prediction corrections.
- `last` is the distance of the latest correction.

The overlay does not read input. Set its public `Visible` field from your own input or UI code. Headless processes do not draw it.

## Enable detailed logs

Pass `-nebula-verbose` to a role to set `NebulaLog.Verbose`. To enable it for a mesh started by the CLI, run `nebula start --verbose` or `nebula deploy --verbose`.

Verbose logging includes process launch arguments, discarded control-plane writes during a disconnection, and message details. Disable it when you measure performance because additional logging can affect tick time.

Use `NebulaLog.Info`, `Warn`, `Error`, and `Debugf` in your own components when you want consistent `[nebula]` prefixes. `Debugf` writes only when verbose logging is enabled.

## Read the worker profile

Every worker writes a profile line every five seconds:

```text
[nebula] profile 300 ticks/5s 300 frames avg 6.8ms max 29.6ms dup 4 skip 0 gc 1 auth 331 ghosts 64 | poll=0.03 ghosts=0.07 physics.sync=0.08 simulate=5.40 poses=0.14 containers=0.56 band=0.26 publish=0.28 gap=9.86
```

Use these fields to find a performance problem:

- `ticks` should average 60 per second, and `frames` should stay close to `ticks`.
- `dup` counts fixed updates that did not advance to a new network tick. An occasional duplicate is expected.
- `skip` counts ticks discarded after the worker fell more than `NebulaWorker.MaxCatchUpTicks` behind. A value that keeps increasing means the worker cannot maintain the tick rate.
- `avg` and `max` report the average and maximum time spent in a Nebula tick.
- `simulate` includes your `NetworkTick` methods.
- `gap` includes work outside the Nebula tick, such as the Unity physics step, `Update`, and idle time.

To profile your own game code, create a section with `NebulaProfiler.Section("name")`, then call `Begin()` and `End()` around the work. The section appears in the worker's profile line.

To read profile lines from a deployed worker, run `nebula logs --cloud w1 -n 300` and filter for `profile`.

## Read the delivery path

A low worker tick time does not mean players see smooth motion: a snapshot still has to cross the worker's transport, the gateway's loop, and the client's frame. Two more telemetry lines cover that path.

The client writes one line every five seconds (`nebula logs bot1`, or the player log):

```text
[nebula] client 142 fps entities 1016 in 866 pkt/s 285.0 KB/s 4901 states/s (msgs: state 1788 rpc 279 vars 810) rtt 0ms lead 5 (adj 2, worker saw 4) corrections 2 last 0.10m | full-rate interp: depth 3.8 ticks, starved 3.0% worst +2.0 | frame max 17.8ms fixed/frame max 1 | gaps>3t 1 worst 176t | render delay 4t (stream lag 1t) | snapshot age ms min 6.5 avg 17.6 max 35.0
```

- `corrections` counts reconciliation snaps of the local pawn; steady non-zero counts with a large `last` distance mean prediction and simulation disagree.
- `full-rate interp` covers entities the gateway sends every tick. `depth` is how many ticks of buffer the interpolator has; `starved` is the share of frames that had to extrapolate past the newest sample. Starvation is what a player sees as remote entities stuttering or rubberbanding.
- `render delay` is `InterpolationDelayTicks` plus `stream lag`, the lateness measured on the slowest worker's stream.
- `snapshot age` is the age of world-state packets on arrival, against the wall clock the workers derive ticks from. On one machine the numbers are exact; across machines read the spread between `min` and `max`, which is the jitter the interpolation delay has to cover.
- `frame max` and `fixed/frame max` show whether the client itself is stalling.
- `carrier hitches` appears while the local pawn rides a carrier (a ship): frame-to-frame jumps of the hull that its reported velocity does not explain, with the carrier's container and epoch changes in the same window. A pilot feels every one of these.

The standalone orchestrator and gateway write a loop line every five seconds:

```text
[nebula] loop 240 Hz, period max 6.1 ms, tick avg 0.08 ms max 0.3 ms
```

`period max` is the longest wait between two loops. The gateway runs four loops per tick; a period well above its interval means the process is not being scheduled on time (on Windows, the service requests a 1 ms timer and opts out of background timer throttling at startup; the log says so).

## Find logs

For a local mesh, find logs in `Builds/<platform>/Logs/`, where `<platform>` is `Win64`, `MacOS`, or `Linux64`.

| File | Process |
| --- | --- |
| `orchestrator.log` | Orchestrator decisions and dashboard events. |
| `gateway.log` | Gateway connections and routing. |
| `w1.log` through `wN.log` | Worker simulation, spawning, peer connections, and handovers. |
| `bot1.log` and later numbers | Bot clients started with `nebula start --bots`. |
| `client123.log` | Extra clients started from the Unity Editor menu. |
| `Builds/unity-build.log` | Latest `nebula build` output. |

For a Hetzner deployment, use `nebula logs --cloud <role>`. The CLI reads the appropriate remote path over SSH. See [Deploy to Hetzner](/docs/deploy/hetzner#operate-the-deployment).

## Inspect status and events

Run these commands from the project directory:

```bash
nebula status
nebula status --json
nebula logs w2 -n 200
nebula logs gateway --follow
nebula logs --cloud w1
```

`nebula status` reads `/api/state` from the local dashboard. Add `--cloud` to read the configured deployment. The command shows worker state, addresses, container assignments, entity counts, tick time, heartbeat age, and recent events.

`nebula logs` prints the last 60 lines from the orchestrator when you omit a role. Pass a role to read another log. Add `--follow` to keep reading a local file as it grows. Cloud logs do not support `--follow`.

The orchestrator keeps its 200 most recent event lines. The dashboard displays the newest 60. Check these events when you need to know when a worker launched, stopped, missed heartbeats, or received a new container assignment.

## Trace a handover

A cross-worker handover produces one line on the previous worker and one on the new worker:

```text
[nebula] handover OUT Player#281474976710659(e3,quadrant-SE,auth) -> w2 (epoch 4, tick 12345)
[nebula] handover IN  Player#281474976710659(e3,quadrant-SE,ghost) <- w1 (epoch 4, tick 12346)
```

The entity format is `name#networkId(e<epoch>,<container>,<role>)`. The high 16 bits of the network ID contain the index of the worker that originally spawned the entity. They do not identify the current worker.

Compare the total `handover OUT` and `handover IN` lines across worker logs. A missing `IN` can mean that the peer connection failed or the receiving worker rejected an old epoch. Search for `peer worker`, `stale authority transfer`, and `not connected; keeping authority` near the same timestamp.

The sending and receiving tick numbers normally match or differ by one.

## Validate the Unity project

Before you build, run **Nebula > Validate Project**. The validator checks build scenes, the game mode, container IDs, network prefab registration, world-partition assets, and other setup that could otherwise fail in a build.

Click a validation message in the Unity Console to select the related asset or GameObject when one is available.

## Use the Editor menu

Use the **Nebula** menu for local development:

- Use **Build** to create a Windows player or Linux dedicated server.
- Use **Mesh** to start or stop the local mesh, launch another client, or open the dashboard.
- Use **World** to author and validate a partitioned world.

For repeatable commands and continuous integration, use the [`nebula` CLI](/docs/cli).

## Troubleshoot common problems

| Symptom | Cause to check | Action |
| --- | --- | --- |
| `nebula build` reports that the project is locked | The Unity Editor has the project open. | Let the CLI build from its mirror. If you passed `--force`, close the Editor and run the command again. |
| Build reports no scenes | The Build Profiles scene list is empty. | Add the boot scene and game scene to **File > Build Profiles**. |
| A remote player does not respond to input | The client's input lead may be too small for the network path. | Open the overlay and compare `lead` with `worker sees`. Increase `InputLeadMarginTicks` or `InputLeadMaxAdjustTicks` if the adaptive lead reaches its limit. |
| Workers remain in `launching` and then disappear | A worker cannot reach the orchestrator's control plane, or presents the wrong mesh token. | Read `w1.log` for `control plane: reading ... failed`. Check the address in `-nebula-control-plane` and that the dashboard port is reachable from the worker. |
| The dashboard is empty | The orchestrator is stopped, uses another port, or cannot bind the dashboard address. | Run `nebula logs orchestrator` and check the reported dashboard URL and bind error. |
| The dashboard reports the control plane stored in `memory` or a storage warning | The orchestrator cannot open its database (`-nebula-database`). | Check `orchestrator.log` for `control plane: saving ... failed` or `persistence: ... failed`. The mesh keeps running; saves resume when the database is back. |
| A worker virtual machine starts but never registers | Its bootstrap could not download the build or discover its private address. | Run `nebula logs --cloud w1` and inspect the bootstrap messages before the worker log. |
| An entity freezes or snaps after `handover IN` | `ReadHandoverState` may not match `WriteHandoverState`. | Search the receiving worker log for a handover-state exception. Read fields in the same order and with the same types used to write them. |
| A worker drains until the timeout | An entity could not transfer or still belongs to an unassigned container. | Compare the worker's `auth` count with its handover lines. Search for transfer and `WriteHandoverState` errors. |
| Many bot clients overload the machine | Each bot is a complete headless Unity client process. | Use only enough bots to test the client path. Create server-driven entities to test simulation load. |
