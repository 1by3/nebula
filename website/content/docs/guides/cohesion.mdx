---
title: Cohesion hints
description: Keep a set of entities on one worker, move them between workers as a unit, and pause rebalancing of a container for a bounded time.
---

Nebula decides which worker simulates which container, and hands an entity over when it crosses into a container another worker leases. Only your game knows which entities must not be separated while that happens: the bodies of one physics island, a player and the crate mid-throw, the two sides of an interaction that is half applied.

Two hints say so.

- A **cohesion group** is a number you put on a set of entities. One worker simulates all of them: a handover of any member takes the others with it, the planner deals their containers as one item, and the [cross-container joint warning](/docs/concepts/distributed-physics) stops firing between them.
- A **hold** asks the orchestrator to leave one container where it is for a few seconds, so a boss fight or a cutscene is not interrupted by a rebalance.

Both are assertions you make. Nebula never infers a group and never checks that one is small enough to fit a worker — if it does not fit, it says so and keeps it whole anyway.

## Cohesion groups

Give every member the same non-zero `CohesionGroup`. Author it on the prefab in the **Cohesion** section of the `NetworkIdentity` inspector, or set it while the game runs:

```csharp
// Everything that will fall apart together belongs to one group.
uint group = (uint)ragdoll.NetId;           // any non-zero number both sides agree on
foreach (var piece in pieces) piece.Identity.JoinCohesionGroup(group);

// ...and when the interaction is over:
foreach (var piece in pieces) piece.Identity.LeaveCohesionGroup();
```

| Member | What it does |
| --- | --- |
| `NetworkIdentity.CohesionGroup` | The group, or `0` for none. |
| `JoinCohesionGroup(uint group)` | Put the entity in a group, leaving the one it was in. |
| `LeaveCohesionGroup()` | Leave the group. Nothing else about the entity changes. |
| `CohesionGroups.Members(group)` | Every copy of a group's entities in this process (authoritative and ghost). |
| `CohesionGroups.Same(a, b)` | Whether two entities are in the same non-zero group. |

The group travels with the entity in its spawn, ghost-spawn and handover messages, so every worker that holds a copy knows it. A group you join **after** an entity is spawned reaches the other workers with that entity's next spawn or handover, so run the join on every copy — game code runs on all of them — rather than only on the authority.

### What a group changes

**Handover.** When a worker hands over any member, it hands over every member it owns, to the same worker, in the same pass. Each member is a normal handover: its own epoch bump, its own ghost, its own redirect. A member that is itself a carrier takes its passengers too.

**Rebalancing.** Each worker reports which of its containers hold members of which group. The planner treats those containers as a single item: they are dealt together, to one worker, exactly like containers sharing an [`AffinityGroup`](/docs/guides/orchestrator-and-dashboard). A group whose members are all in one container binds nothing.

**Physics diagnostics.** A `Joint` between two entities in one cohesion group is no longer reported as crossing containers: you promised one worker simulates both.

### When a group cannot be honoured

Nebula never splits a group quietly. There are two ways it can fail, and both are reported.

- A worker hands over a member while another member is owned by a *different* worker. The worker cannot move what it does not own, so it logs a warning naming the group and counts it in `NebulaDiagnostics.SplitCohesionGroups`. The handover still happens — refusing it would strand the entity on a worker that no longer leases its container — and the next planning pass puts the group's containers back on one worker.
- The group's containers together cost more than one worker's tick budget. The planner deals them to one worker anyway and adds a row to the dashboard's **Cohesion** card and to the orchestrator log: which group, which containers, what it costs. Make the group smaller, or give the mesh bigger workers.

## Rebalancing a hot area

A group and a hold are constraints on the planner, not obstacles to it. When one area of the world runs hot, the planner re-deals the containers the game authored there to more workers, cutting between two of them along the boundaries your [hints](/docs/guides/orchestrator-and-dashboard#balancing-hints) describe — `seam=` says a cut beside a container is expensive, `x2` says it is heavier than its occupancy suggests, `group=` says two containers are dealt as one. Cohesion groups join that list from the other side: the planner treats the containers a group spans as one item and cuts somewhere else.

A city authored as six districts with an `x2` hint therefore spreads across workers district by district, and a docked fleet in two of those districts moves as a unit or not at all. The district where the fight is happening stays where it is for as long as its worker holds it.

What Nebula will **not** do is subdivide one container, or copy the area and split the players between the copies. If one container is carrying a whole worker on its own, there is no cut to make, and the planner says so instead of shuffling containers pointlessly:

```
no boundary hint: plaza carries 0.92 of a tick on its own and the game authored no boundary inside it
(bake it as more cells, register runtime containers, or hint a seam); Nebula never subdivides a container
```

That report — with the cause `cohesion-group`, `affinity-group`, `held`, `dedicated` or `no-boundary` — appears on the dashboard's **Assignment plan** card, in `assignment.saturated` of `/api/state`, and in the autoscaler's blocked reason, so a mesh that has stopped growing always says which constraint stopped it. Every move the planner *does* make is listed on the same card with the boundary it cut along and the load numbers behind it.

## Holds

A hold is a worker saying "do not rebalance this container for the next few seconds".

```csharp
// The boss fight has started: do not move this container out from under it.
worker.HoldContainer(arena, 30f);

// ...and when it is over, before the hold runs out:
worker.ReleaseHold(arena.ContainerId);
```

| Member | What it does |
| --- | --- |
| `HoldContainer(Container c, float seconds)` | Ask for a hold. Repeating extends it; it never shortens an existing one. |
| `HoldContainer(string containerId, float seconds)` | The same by id, for a container this worker does not hold an object for. |
| `ReleaseHold(string containerId)` | Drop the hold early. `HoldContainer(c, 0)` does the same. |
| `HoldRemaining(string containerId)` | Seconds left, or 0. |
| `NebulaWorker.MaxHoldSeconds` | The ceiling, 120 seconds. Longer requests are clamped. |

A hold is a pause, not a pin:

- It is **bounded**. The longest one is two minutes, and it expires by itself.
- It **dies with its worker**. The orchestrator keeps holds per worker and drops them when that worker stops reporting, so a crash cannot freeze the layout.
- It **never leaves a container unowned**. If nobody owns the container — a fresh mesh, a dead worker — it is placed regardless.
- It applies to the whole item. Holding one container of a cohesion or affinity group holds the group, because moving the rest would be the split the group exists to prevent.

For something permanent, use a container hint instead: `dedicated` gives a container a worker to itself, and a [carried container](/docs/guides/dynamic-containers) can be pinned.

### Clocks

The worker reports how many seconds a hold still has to run; the orchestrator turns that into a deadline on its own clock the moment the report arrives. The two processes need no common time base and no clock synchronisation — only monotonic clocks that run at about the same rate. The cost is the telemetry hop: a hold reaches the orchestrator up to a second after you asked for it, and is that much shorter as the planner sees it.

## On the dashboard

The **Cohesion** card of the [orchestrator dashboard](/docs/guides/orchestrator-and-dashboard) lists every live hold (container, worker, seconds left) and every cohesion group (id, members, the containers it spans, the workers holding it). A group on more than one worker is flagged, and a group that does not fit one worker is shown as a warning above the table. The card hides itself when there is nothing to show.
