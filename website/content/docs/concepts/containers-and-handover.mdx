---
title: Containers and handover
description: How containers determine worker authority and how Nebula transfers an entity across a container boundary.
---

Use containers to decide which worker controls each entity. When an entity approaches a container owned by another worker, Nebula sends that worker a non-authoritative copy called a **ghost**. When the entity crosses the boundary, Nebula transfers authority and the latest state to the new worker. Nebula calls this operation a **handover**.

## Containers

Add the `Container` MonoBehaviour to a scene object to create a box volume. The object's transform defines the container's local coordinate space. When you add the component in the Editor, Nebula gives it a random `ContainerId` and sets `Size` and `Center` to the bounds of the object's renderers, or its colliders when it has no renderers. To wrap the box around the object again after you change it, select **Fit Size and Center to Bounds** in the Inspector. You can also call `FitToBounds()` from code. Keep the ID stable after the scene is in use.

Nebula parents contained entities under the container transform and sends positions in that local space. Moving the container therefore does not change the local coordinates of its contents.

A container authored in a scene is **static** and assigned to a worker. A container created with an entity is **dynamic**. It moves with that entity and normally follows the entity's worker. This page focuses on static containers. See [Dynamic containers](/docs/guides/dynamic-containers) for moving containers.

At startup, `ContainerRegistry.Rebuild()` collects the containers in the loaded scene. It sorts them by ID and assigns each one an `Index`. Nebula uses the ID for control-plane assignments and the smaller index in network messages.

`ContainerRef` identifies a static container by its index. It identifies a dynamic container by the network ID of its carrier.

Nebula treats two containers as neighbors when their bounds touch or overlap. The registry records static neighbors in `Neighbors`. Call `ContainerRegistry.NeighborsOf` when you also need dynamic containers that currently touch the volume.

Read `OwnerWorkerId`, `OwnerWorkerIndex`, and `LeaseEpoch` to inspect a container's current assignment. Use `IsOwnedBy`, `Contains`, and `SignedDistance` for ownership and bounds checks. Use `ToLocal` and `ToWorld` to convert positions.

Seams are implicit: every container boundary carries two parameters from `NebulaConfig`:

| Parameter | Default | Effect |
| --- | --- | --- |
| `GhostBandMargin` | 4 m | An authoritative entity within this distance of a neighbouring container owned by another worker is ghosted there ahead of time. |
| `HandoverHysteresis` | 0.35 m | An entity must be this far inside a new container before authority flips, so an entity dithering on the line does not thrash. |
| `GhostLingerSeconds` | 2 s | A ghost stays resident this long after its entity leaves the band, so a quick return is free. |

You do not need to create separate boundary or transition objects.

## Leases and epochs

The orchestrator writes one `container_lease` row for each static container. This row records the container ID, worker ID, epoch, and state. Every 500 milliseconds, the orchestrator distributes containers across active workers. It keeps current assignments when possible so a rebalance moves fewer containers.

When the orchestrator assigns a container to a different worker, it increments the assignment's **lease epoch**. An epoch is a number used to order ownership changes.

Every entity has its own authority `Epoch`, which increases when its controlling worker changes. Entity messages include the network ID and epoch. The gateway and workers reject a message with an older epoch or an invalid sender. This prevents two workers from controlling the same entity after a temporary disagreement.

## The worker's tick

Each worker calculates its current tick from the wall clock and a fixed origin with `NetworkTime.DerivedTick`. This keeps tick numbers aligned without a coordinator. On every tick, a worker:

1. Moves the ghosts it holds to the pose their owners streamed (kinematic, no physics solve of their own; `RemoteTick` on their behaviours presents the sync channel).
2. Runs `NetworkTick` (and therefore `Simulate` on predicted behaviours) on every entity it has authority over, then lets PhysX step.
3. Re-evaluates container membership for its authoritative entities, with hysteresis, and transfers authority for entities that crossed into a container owned by another worker.
4. Maintains the **ghost band**, which is the area within `GhostBandMargin` of a neighboring container. It sends `GhostSpawn` once, `GhostState` for changed root transforms and reliable placement or recovery updates, `GhostVars` when a `NetworkVariable` changes, and `GhostSyncState` for component sync data. It sends entities in a dynamic container to each worker that has a ghost of the carrier.
5. Streams `WorldState`, `OwnerState`, `EntityVars` and `EntityState` for its authoritative entities to the gateway.
6. Records every resident entity's pose for the lag-compensation history (`NetworkIdentity.TryGetPoseAt`).

Workers discover each other through the control plane and peer directly over UDP; the lower index dials.

## What a ghost is

On a worker that does not control it, an entity exists as a ghost. `GhostSpawn` identifies the prefab and includes its container, pose, velocity, `NetworkVariable` values, and component sync keyframes.

On a ghost, `IsGhost` is `true` and `HasAuthority` is `false`. Nebula does not call `NetworkTick`, allow `NetworkVariable` writes, or send `ClientRpc` from that copy. A ghost can send `AuthorityRpc` to the entity's worker. The worker makes a ghost's `Rigidbody` kinematic, with or without `NetworkRigidbody`.

An enabled `NetworkTransform` moves a ghost from state sent by its controlling worker. Without one, the ghost keeps its initial placement until a container change or new spawn snapshot. Local raycasts and dynamic entities can detect the ghost. A local entity can collide with and respond to a ghost, but the collision does not change the ghost on its controlling worker.

The neighbour thus holds full warm state before the entity can cross. If the entity leaves the band without crossing, the ghost lingers for `GhostLingerSeconds` and is then despawned.

For what a collision with a ghost does and does not do, and why a joint across two workers is unsupported, see [Distributed physics](/docs/concepts/distributed-physics).

## Complete the handover

When an entity moves farther than `HandoverHysteresis` into a container assigned to another worker, the current worker sends a reliable `AuthorityTransfer` message. It contains:

- the entity's complete final position and rotation in the new container's local space, local scale, and world-space velocity, even when ongoing transform synchronization omits those values,
- the new epoch,
- the full NetworkVariable blob,
- the not-yet-simulated inputs buffered for a predicted behaviour, so the input stream never breaks,
- a keyframe of the sync channel,
- whatever each behaviour wrote in `WriteHandoverState` (angular velocity for a rigidbody, timers, RNG state),
- the flags that say whether the entity is owned by a bot or is server-driven, so the per-worker counts stay right.

On the sending worker, the entity becomes a ghost and `OnLostAuthority` runs. For a short time, that worker forwards input that still arrives from the gateway.

On the receiving worker, Nebula updates the existing ghost or creates the prefab when no ghost exists. It applies the transferred state, calls `ReadHandoverState`, and then calls `OnGainedAuthority`. The entity becomes authoritative on the next tick.

Both workers report the change to the gateway. The gateway then accepts the new epoch and routes the owning client's input to the new worker.

If the two containers are owned by the same worker, none of this leaves the process: the entity is reparented, `OnContainerChanged` fires and `LocalHandovers` ticks up.

When the entity that crosses carries a container of its own, everything inside that container is transferred right after it, in the same tick and on the same ordered channel: a ship crossing a seam takes its crew along, and their container-local poses never change.

The client's copy keeps the same network ID during a handover. New snapshots include the updated epoch and worker index. The owning client can continue prediction because the transfer includes pending input.

## Cross-container interaction

Use `[AuthorityRpc]` to apply an interaction to an entity controlled by another worker. For example, a worker can raycast against a ghost and call a damage method on the target. Nebula calls the method locally when the same worker controls both entities. Otherwise, it sends the call to the target's worker.

Nebula does not automatically validate the claim on the receiving worker. Implement validation in your game when needed. Use `NetworkIdentity.TryGetPoseAt` to read recorded poses for a lag-compensated query. See [Prediction](/docs/guides/prediction).

## Container reassignment

When a container assignment changes, the previous worker sends one `AuthorityTransfer` for each authoritative entity in that container. Nebula does not currently prepare the new worker before changing the assignment. Persisted entities are read only after the new owner has held the lease for a grace period, so a handover always wins over a restore.

When you remove a worker, the orchestrator keeps it running until it has no assignments and reports no authoritative entities. It stops waiting when `WorkerDrainTimeoutSeconds` expires.

If a worker stops unexpectedly, its transient entities are lost. Entities carrying a `PersistentEntity` come back from their last checkpoint once another worker has held the container's lease for `NebulaConfig.PersistenceRestoreGraceSeconds`; see [Persistence](/docs/guides/persistence). The orchestrator reassigns its containers, and the gateway requests replacement player entities from another worker.

## Tuning

Increase `GhostBandMargin` if fast entities reach a boundary before the next worker receives a ghost. A receiving worker that must create a new instance during handover is a sign that the margin may be too small.

Increase `HandoverHysteresis` if an entity near a boundary repeatedly moves between workers. To test values for one run, use `-nebula-ghost-band` and `-nebula-hysteresis`.

## Partitioned worlds

For a world larger than one scene, use [world partition](/docs/guides/world-partition) to make each grid cell a container. Containers authored inside a cell become its children.

Nebula reads this container tree from a baked manifest. The manifest keeps container indices consistent while each process loads only the cells it needs.
