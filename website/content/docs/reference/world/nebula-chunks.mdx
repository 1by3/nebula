The content-streaming face of a chunked world: one place, on every role, where a game is told which chunks exist. [`NebulaBootstrap`](/docs/reference/bootstrap/nebula-bootstrap) activates it from [`NebulaConfig.ChunkedWorld`](/docs/reference/core/nebula-config#chunkedworld) plus a [`NebulaConfig.RuntimeWorld`](/docs/reference/core/nebula-config#runtimeworld); a game supplies content and nothing else.

Chunks are Nebula runtime containers, so "which chunks exist" means something slightly different per role and that is exactly the point: a worker sees the cells it and its neighbors lease, a client sees the containers the gateway told it about (its interest window), and both learn about them through the same two events. A game's callback therefore never needs to know which role it is running on, nor to poll.

[`Loaded`](#loaded) back-fills: subscribing after chunks already exist raises the event for each of them at once, so a handler added from `Start` on a late-loaded scene object cannot miss a chunk and no game has to write the "and now walk the existing ones" loop that every hand-rolled chunk loader begins with.

### EnsureAt [#ensureat]

```csharp
public static void EnsureAt(Vector3 framePosition, Action<Container> onReady);
public static void EnsureAt(Vector3Int coord, Action<Container> onReady);
```

Make sure the chunk holding `framePosition` exists, then hand it over. The spawn-point helper: a game mode that wants to put a player or an object somewhere must not assume a container is there, and must not poll for one either. On a worker this requests the lease; on any role it waits for the registration event, and calls back at once when the chunk is already here.

The deterministic per-chunk seed ([`ChunkContext.Seed`](/docs/reference/world/chunk-context#seed)). A 64-bit finalizer mix of the packed id, so neighboring coordinates — whose ids differ in one low bit — produce unrelated seeds. Never zero-sensitive: chunk (0,0,0) gets a seed like any other.
