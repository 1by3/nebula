The gateway's admission rules for a client request, in one place and with no engine types, so the gateway, the standalone services and the tests run the same code. The rules, in the order they are checked; the first that fails decides:

1. The arguments are larger than [`MaxBytes`](#maxbytes): [`ClientRequestOutcome.RejectedTooLarge`](/docs/reference/protocol/client-request-outcome#rejectedtoolarge).
2. The gateway has no such entity: [`ClientRequestOutcome.RejectedUnknownEntity`](/docs/reference/protocol/client-request-outcome#rejectedunknownentity).
3. The entity is not in the sender's interest set: [`ClientRequestOutcome.RejectedNotInInterest`](/docs/reference/protocol/client-request-outcome#rejectednotininterest).
4. The sender is over its rate: [`ClientRequestOutcome.RejectedClientRateLimit`](/docs/reference/protocol/client-request-outcome#rejectedclientratelimit). A request that gets this far spends one of the sender's tokens, whatever happens next, so a client cannot flood a busy entity for free.
5. The entity is over its rate, across every sender: [`ClientRequestOutcome.RejectedEntityRateLimit`](/docs/reference/protocol/client-request-outcome#rejectedentityratelimit).

Size, existence and interest are checked before either rate so a request that was never going to be delivered does not spend a token or create a bucket for an entity the sender cannot see.
