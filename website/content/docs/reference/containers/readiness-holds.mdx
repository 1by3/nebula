The application's say in a portal link's readiness (`docs/portals.md` D10, condition 6): the worker that owns a container can hold it "not ready yet" while it does something the game needs done before anyone comes through, such as spawning the population of a level the link leads into. A link whose far window touches a held container stays [`PortalState.Preparing`](/docs/reference/protocol/portal-state#preparing) with [`PortalWait.FarContentHeld`](/docs/reference/protocol/portal-wait#farcontentheld), whichever worker owns the portal: a far worker answers the link's preparation (D35) only once its container is released.

A hold is named by a reason, so independent systems can hold one container and each releases only its own. It holds a link that is preparing; a link that is already open stays open. It is local to the process that placed it: it lives on the worker that owns the container, and a container that moves to another worker is not held there (that worker's application holds it again if it should).

**It never wedges a link.** Every hold expires `timeoutSeconds` after it was placed (by default [`DefaultTimeoutSeconds`](#defaulttimeoutseconds)) even if nobody releases it, with a warning: the application should release sooner, and a hold placed again restarts its clock.
