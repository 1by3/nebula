### CorrectionSmoothingSeconds [#correctionsmoothingseconds]

```csharp
protected virtual float CorrectionSmoothingSeconds { get; }
```

Owning client: how long a correction takes to fade from the screen, in seconds. When the worker's state disagrees with the prediction, the simulated state moves to the corrected one at once (the replay is exact), but the entity is *drawn* at an offset from it that starts at where it was last drawn and decays exponentially: the offset falls to 1% of its size after this long. Offsets from corrections that arrive faster than they decay add up. Default 0.1 (100 ms); 0 or less turns smoothing off, so the drawn pose snaps with the simulated one.

### DriverInputTimeoutTicks [#driverinputtimeoutticks]

```csharp
protected virtual int DriverInputTimeoutTicks { get; }
```

Ticks without any input from the driver after which the worker stops repeating the last one and runs [`PredictedBehaviour<TInput>.GatherServerInput`](/docs/reference/core/predicted-behaviour#gatherserverinput) instead, until the driver's input comes back: a driver whose link drops does not leave the vehicle at full throttle. ### StepSkippedServerTicks [#stepskippedserverticks]

```csharp
protected virtual bool StepSkippedServerTicks { get; }
```

Whether the worker, after it skipped tick numbers because it fell too far behind the wall clock, steps this entity through each skipped tick that has an input waiting before it simulates the next one (NEB-412). The owner predicted every one of those ticks with its input, so an entity that is left out ends the next tick short of where its owner has it and is corrected. Return true when `Simulate` advances the entity itself and is a pure function of state and input, as the owner's replay already requires: each skipped tick then runs exactly as the replay runs it and the entity ends where its owner has it. Leave it false when `Simulate` relies on the physics engine stepping between ticks (it applies forces or sets a Rigidbody's velocity): the skipped ticks would apply their forces back to back before one physics step and the entity would lurch, so it is corrected after a skip instead. Default false.

```csharp
protected virtual void OnDriverChanged(ulong previous, ulong current);
```

The driver of this entity changed ([`NetworkIdentity.SetDriver`](/docs/reference/core/network-identity#setdriver)): `current` is the new driver's client id, 0 when nobody drives it now. Called on the worker that has authority when the change is made, and on every client that holds the entity when it hears of it, the new and the previous driver's included. Use it for what the seat does (a camera, a HUD, handing the controls back to the worker's own logic); Nebula has already switched the input source and the prediction.

### PostServerEvent [#postserverevent]

```csharp
public bool PostServerEvent<TEvent>(in TEvent e)
    where TEvent : struct, INetworkSerializable;
```

Authority only: attach an event to the next tick this entity simulates, so its `Simulate` sees it there with [`TryGetServerEvent<TEvent>`](#trygetserverevent). The owner's client is sent the event with its state reports and keeps it, so its prediction replays the event on the same tick, and it travels with the entity when another worker takes it over, without applying twice. Use it for what the worker decides and the owner cannot know: a shove, a stun, a forced move.

At most [`MaxServerEventsPerTick`](#maxservereventspertick) events apply on one tick; the next is refused, counted in [`ServerEventsDropped`](#servereventsdropped), and this returns false. It also returns false, with a warning once, on a copy without authority. `TEvent` is identified on the wire by a hash of its full name, so use a distinct struct for each kind of event.

### TryGetServerEvent [#trygetserverevent]

```csharp
protected bool TryGetServerEvent<TEvent>(out TEvent e)
    where TEvent : struct, INetworkSerializable;
protected bool TryGetServerEvent<TEvent>(int index, out TEvent e)
    where TEvent : struct, INetworkSerializable;
```

Inside `Simulate`: the server event of type `TEvent` posted for the tick being simulated, if any. It is there on the authoritative worker, in the owner's replay of that tick and in the owner's own simulation of it once its client has heard of the event. Apply it to simulated state (velocity, a stun timer: whatever `WriteState` carries) so that the owner's replay ends where the worker did. Outside `Simulate` it finds nothing.
