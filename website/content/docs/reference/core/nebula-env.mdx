A game's own settings and secrets on a worker (service URLs, API keys, feature flags): the environment variables set with `nebula env`, in the Nebula Cloud dashboard, or in `.env.nebula` for local runs.

[`Get`](#get) looks a variable up in this order and returns the first value it finds:

1. The command line: `-game-api-url <value>` (or `=value`) for `GAME_API_URL`. The switch is the name in lower case with `_` turned into `-` ([`ArgName`](#argname)). A web build reads it from the page's query string instead.
2. The process environment: `GAME_API_URL` ([`EnvName`](#envname)). Deployed workers get their variables here: Nebula Cloud and `nebula deploy` set them before the worker starts.
3. The files Nebula loaded for this process: the file `NEBULA_ENV_FILE` names, when the process that started the worker did not apply it, and in the Editor the project's `.env.nebula`.
4. `fallback`.

Either spelling of a name works: `Get("GAME_API_URL")` and `Get("game-api-url")` look up the same variable. Nebula never logs a variable's value.

### LoadFile [#loadfile]

```csharp
public static int LoadFile(string path);
```

Read a dotenv file into the file layer of [`Get`](#get) and copy its variables into this process's environment, where the environment does not already have them, so code that reads `Environment.GetEnvironmentVariable` sees them too. Variables a previous call copied are replaced or removed. Reserved names (`PORT`, `NEBULA_*`) are skipped with a warning.

**Returns:** How many variables were loaded; 0 when the file does not exist.
