Run the commands on this page from a Unity project where you have already run `nebula init`. You can also run the same operations from the **Nebula** menu in the Unity Editor.

## Build

```bash
nebula build
nebula build --linux
nebula build --web
```

To build the game for your current platform, run `nebula build`. The command reads the required Unity version from `ProjectSettings/ProjectVersion.txt`. It finds that version through Unity Hub, `NEBULA_UNITY`, or the path saved by `nebula config unity`.

On Windows, the default output is `Builds/Win64/Nebula.exe`. Set `executable` in `nebula.json` to change the base name. To build a Linux dedicated server, run `nebula build --linux`. This command writes the server to `Builds/Linux64` and creates `Builds/nebula-linux.tar.gz` for deployment. To build a client that runs in a browser, run `nebula build --web`. It writes `Builds/Web`, which the local gateway serves. See [Build for the web](/docs/guides/web-builds).

You can keep the project open in the Unity Editor while you build. The CLI copies the project to `~/.nebula-cli/scratch/<project>`, builds the copy, and writes the result to your project's `Builds/` folder.

The CLI prints compiler errors and lines tagged `[nebula]`. To read the complete build log, open `Builds/unity-build.log`. If a running mesh has locked the previous build, run `nebula build --stop-mesh` to stop it before building.

After a wire-protocol change, rebuild and restart the mesh as well as any standalone or web clients. Compiling scripts in the Editor does not update running services. A gateway warning such as `client protocol 12 != 11; disconnecting` means the client and gateway versions differ. See [Rebuild after a protocol change](/docs/guides/instancing#rebuild-after-a-protocol-change).

## Start

```bash
nebula start --open-ui
nebula start --workers 2 --bots 2
```

When you run `nebula start`, the CLI:

1. Launches the orchestrator from the last build with its database at `Library/Nebula/nebula.db` (`mesh.database` in `nebula.json` changes it). The orchestrator hosts the control plane on the dashboard port, launches the gateway and the number of workers set by `--workers`, and assigns each container to a worker.
2. Launches `--bots` bot clients.
3. Waits for the dashboard and prints how to join.

Saved entities stay in the database across restarts; add `--reset-persistence` to start from an empty world.

Set local defaults in the `mesh` section of `nebula.json`. To build before starting, add `--build`.

### Joining

To join from the Unity Editor, enter Play mode. `NebulaBootstrap.EditorRole` uses `Client` by default. See [Choosing the Editor's role](#choosing-the-editors-role) to run a worker in the Editor instead.

To join from a standalone build on Windows, run:

```bash
Builds\Win64\Nebula.exe -nebula-role client -nebula-name Player
```

If your scene includes `NebulaTitleScreen`, enter the gateway address and a display name on the title screen, then select **Connect**. Use `127.0.0.1:7000` for a local mesh. Press Escape during the game to disconnect or choose another gateway. **Nebula > Set Up Active Scene** adds the title screen for you.

To join from a browser, run `nebula build --web`, then open `http://127.0.0.1:7000/`.

Without `NebulaTitleScreen`, a client started without connection arguments stays idle until your code calls `NebulaClient.ConnectTo`. See [Connecting clients](/docs/guides/connecting-clients).

To connect without any UI, pass `-nebula-gateway <address:port>` or `-nebula-connect`. Bot clients also connect at startup. The title screen stays hidden for these clients.

### Test with bots and server-driven entities

Use bots to test the complete client path. Use server-driven entities to test worker simulation without starting more client processes.

| | Bot | Server-driven entity |
| --- | --- | --- |
| Start it with | `nebula start --bots N` | `NebulaWorker.SpawnServerDriven` in your game code |
| What it is | A headless client that connects through the gateway, predicts, and corrects its state like a player | A networked entity with no owning client, simulated by its authoritative worker |
| Runtime cost | One Unity player process | One simulated entity |
| Use it for | Testing the complete client connection, prediction, and reconciliation path | Testing server-side entity load |

Your game must provide bot input and server-driven behavior. Nebula does not provide an NPC implementation. See [Spawning](/docs/guides/spawning) for the server-driven API.

## Choosing the Editor's role

`NebulaBootstrap.EditorRole` sets the roles the Editor starts when you press Play. The Editor has no command line, so this field takes the place of `-nebula-role`. On its own, it does **not** let you skip `nebula build` and `nebula start`:

- **A process is a client or a worker, never both.** If `EditorRole` includes both, Nebula drops the worker role and logs an error. Whichever half the Editor does not run must come from a build, or from a second Editor process. See [Iterate without building](#iterate-without-building-multiplayer-play-mode).
- **The orchestrator launches processes from a build.** It starts the gateway and every worker as a separate player process. In the Editor there is no player executable to reuse, so an Editor orchestrator logs `executable not found` unless `NebulaConfig.WorkerExecutable` points at a build.
- **Workers and the gateway need an orchestrator.** They mirror the control plane from the orchestrator at `NebulaConfig.ControlPlaneUrl` (default `http://127.0.0.1:7080/`). `nebula start` is what starts it.

| `EditorRole` | Start first | Use it for |
| --- | --- | --- |
| `Client` (default) | `nebula build`, then `nebula start` | Playing and debugging client code: input, prediction, UI. |
| `Worker` | `nebula build`, then `nebula start --workers 0` | Debugging worker code (the game mode, `Simulate` on the authority, RPC handlers) with breakpoints. Join with a client build. |
| `Worker`, `Gateway`, `Orchestrator` with `UseLocalControlPlane` | `nebula build` for the client only | A one-worker server in a single process, without a standalone orchestrator. |

### The Editor as a worker

```bash
nebula build
nebula start --workers 0
```

With `EditorRole` set to `Worker`, press Play. The Editor worker uses the defaults for a worker without command-line switches: ID `w1`, index 1, port `WorkerBasePort + 1` (7101). If the environment the Editor started from sets `PORT`, the Editor worker listens on that port instead. Starting the mesh with `--workers 0` keeps a launched worker from already using that ID and port. The orchestrator sees the Editor worker register and gives it every container.

Join with **Nebula > Mesh > Launch Extra Client Window** or `Builds\Win64\Nebula.exe -nebula-role client -nebula-name Player`. To test handovers, select **Add worker** on the dashboard: the orchestrator launches `w2` from the build, and the containers are split between the two.

When you exit Play mode, the Editor worker stops sending heartbeats. After `WorkerTimeoutSeconds` the orchestrator treats it as dead and releases its containers to any remaining worker. It does not relaunch the Editor worker; press Play again.

### Everything server-side in the Editor

Set `EditorRole` to `Worker`, `Gateway` and `Orchestrator`, and enable `UseLocalControlPlane` on `NebulaConfig`. The three roles share an in-process [`LocalControlPlane`](/docs/guides/control-plane#the-three-implementations), so nothing else needs to run. Because nothing outside the process can see that control plane, the orchestrator does not launch the gateway or workers. The in-process worker gets every container and the in-process gateway listens on `GatewayPort`. Join from a client build as above.

This mode has limits:

- There is exactly one worker, so there are no handovers, ghosts or cross-worker RPCs to test.
- Persistence in `auto` mode writes to a local file under `Application.persistentDataPath`.
- `UseLocalControlPlane` is saved in the config asset that builds also load. Turn it off again before running `nebula build` for `nebula start` or a deployment. Otherwise, the built orchestrator also uses a local control plane and never launches the gateway or workers.

## Iterate without building: Multiplayer Play Mode

To play your game in the Editor without running `nebula build` and `nebula start`, use Unity's Multiplayer Play Mode. It runs a *virtual player*: a second Editor process that shares your project. With `NebulaConfig.EditorRunMode` set to `MultiplayerPlayMode`, the virtual player hosts the server and the main Editor is a client. Each process still has one side: the virtual player is the worker, and the main Editor is the client.

### Before you start

- Use Unity 6.6 (6000.6) or later. Earlier Unity 6 versions can work if the Multiplayer Play Mode package provides its player API. If Nebula cannot read it, it runs as `Mesh` and logs a warning.
- Add the `com.unity.multiplayer.playmode` package with the Package Manager.
- Open **Window > Multiplayer > Multiplayer Play Mode** and enable one virtual player.

### Turn it on

1. Select `NebulaConfig` (**Nebula > Select Config**).
2. Set **Editor Run Mode** to `MultiplayerPlayMode`.
3. Press Play.

The virtual player runs the orchestrator, the gateway and one worker in one process. The control plane stays in memory, and autoscaling is off. The main Editor waits until that server is listening, then connects to it. The title screen stays hidden. Each process logs the side it took, for example:

```text
[nebula] editor run mode: Multiplayer Play Mode (this virtual player hosts the server)
```

The setting affects only the Editor. Builds ignore it. The settings it implies are applied to the Editor's copy of the config, never to the asset. So you do not have to change anything back before `nebula build`. A command-line switch such as `-nebula-role` or `-nebula-workers` still wins.

To add a second player, enable another virtual player and give it the `Client` tag in the Multiplayer Play Mode window. A virtual player tagged `Server` hosts the server. With no tags, the main Editor is the client and a virtual player is the server. Run only one server.

### Saved entities

`NebulaConfig.EditorPersistence` chooses what the server does with [persistent entities](/docs/guides/persistence):

| Value | Behavior |
| --- | --- |
| `DevSaveFile` (default) | Keeps them in `Library/Nebula/DevSaves/world.bin` from one Play to the next. The file is separate from the database that `nebula start` uses. |
| `InMemory` | Starts every Play from an empty world. |

To start from an empty world once, stop Play and choose **Nebula > Dev Loop > Reset Dev Saves**. This deletes the dev save file.

### Ports

Both sides add `NebulaConfig.EditorPortOffset` (default `50`) to `GatewayPort`, `WorkerBasePort` and `DashboardPort`. With the default ports, the gateway listens on 7050, the worker on 7151, and the dashboard on `http://localhost:7130/`. So a mesh started with `nebula start` can run at the same time. Set the offset to `0` to use the configured ports.

A client in this mode connects only to the server its own Play session started. The server records its port, or the reason it could not start, in `Library/Nebula/dev-session.json`. If another process holds the server's port, the client connects to nothing and logs the server's error, for example:

```text
The Editor-hosted server could not start (could not bind udp/7050: another process is using it, ...). A client of this session does not join any other server. Stop the other mesh (nebula stop) or change NebulaConfig.EditorPortOffset, then press Play again.
```

If no server starts within 20 seconds, the client logs how to enable a virtual player, then keeps waiting.

### What it does not test

The server runs exactly one worker, so this mode cannot test anything that needs two:

- Container boundaries between workers
- Handovers
- Ghosts and cross-worker RPCs
- Recovery from a failed worker

To test these, run `nebula build` and `nebula start` with more than one worker, or add a worker from the dashboard.

### The server renders nothing

The server turns off every camera, so its Game view stays empty. That is by design: it has nothing to show. It also works around a known problem. On Unity 6000.6, a virtual player cannot compile the Universal Render Pipeline's (URP) shaders, which leaves a black screen and fills its log with shader errors. For the same reason, a virtual player tagged `Client` in a URP project may not render.

## Watch

```bash
nebula status
nebula logs w1 --follow
nebula logs gateway -n 200
```

Run `nebula status` to list workers, their assigned containers, entity counts, and recent orchestrator events.

Run `nebula logs <role>` to read a log. Use `orchestrator`, `gateway`, `w1` through `wN`, or `bot1` and later bot numbers as the role. The CLI stores logs in the build's `Logs/` folder.

To inspect a local mesh in a browser, open `http://localhost:7080/`. The dashboard shows the gateway address, workers, entity counts, tick times, heartbeat ages, container assignments, settings, and recent events.

Use the dashboard controls to add a worker, drain and remove a worker, stop a worker to test recovery, or rebalance containers. You can also perform these operations through the [dashboard HTTP API](/docs/guides/orchestrator-and-dashboard).

If your scene includes `NebulaDebugOverlay`, press F3 to show or hide it. The overlay displays the tick, round-trip time (RTT), input lead, current container, current worker, observed handovers, and container assignments.

## Stop

```bash
nebula stop
```

Run `nebula stop` to stop every process from the build: the orchestrator, the gateway, the workers, and any bots. The database file stays where it is.

## From the Editor

Use the **Nebula** menu in the Unity Editor to run the same development tasks:

- Use **Mesh** to start or stop a local mesh from the latest build, open the dashboard, or launch another client.
- Use **Build** to create a Windows player or Linux dedicated server.
